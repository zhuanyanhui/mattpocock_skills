# Codebase Design

设计**深度模块（deep modules）**：在小接口背后隐藏大量行为，放置于干净的 seam（接缝）上，并通过该接口进行测试。在设计和重构代码时使用这套语言和原则。目标是调用者的 leverage（杠杆效应）、维护者的 locality（局部性）和所有人的可测试性。

## 词汇表

精确使用这些术语——不要用"component"、"service"、"API"或"boundary"替代。一致的词汇才是关键所在。

**Module（模块）** — 任何有接口和实现的东西。刻意与规模无关：一个函数、类、包或跨层级切片。_避免_：unit、component、service。

**Interface（接口）** — 调用者正确使用模块所需了解的一切：类型签名，还包括不变量、顺序约束、错误模式、所需配置和性能特征。_避免_：API、signature（太窄——它们仅指类型层面的表面）。

**Implementation（实现）** — 模块内部的内容，其代码主体。与 **Adapter（适配器）** 不同：一个东西可以是小适配器大实现（Postgres 仓库）或大适配器小实现（内存 fake）。当讨论 seam 时使用"adapter"；其他情况使用"implementation"。

**Depth（深度）** — 接口处的杠杆效应：调用者（或测试）每学习一单位接口所能运用的行为量。当一个模块在**小接口**背后隐藏**大量行为**时是**深（deep）** 的；当接口几乎与实现一样复杂时是**浅（shallow）** 的。

**Seam（接缝）** _（Michael Feathers）_ — 你可以在不编辑某处的情况下改变行为的位置；模块接口所在的*位置*。将 seam 放在哪里本身就是一个设计决策，与它背后是什么不同。_避免_：boundary（与 DDD 的有界上下文重载）。

**Adapter（适配器）** — 在 seam 处满足接口的具体实现。描述*角色*（它填充什么插槽），而非实质（内部是什么）。

**Leverage（杠杆效应）** — 调用者从深度中获得的东西：每学习一单位接口获得更多能力。一个实现在 N 个调用点和 M 个测试中回报。

**Locality（局部性）** — 维护者从深度中获得的东西：变更、bug、知识和验证集中在一个地方，而不是分散在调用者之间。一次修复，处处修复。

## 深与浅

**深度模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   小接口             │  ← 少方法，简单参数
├─────────────────────┤
│                     │
│   深度实现           │  ← 复杂逻辑隐藏在内
│                     │
└─────────────────────┘
```

**浅度模块** = 大接口 + 少量实现（避免）：

```
┌─────────────────────────────────┐
│       大接口                     │  ← 多方法，复杂参数
├─────────────────────────────────┤
│  薄实现                          │  ← 仅透传
└─────────────────────────────────┘
```

设计接口时，问：

- 能否减少方法的数量？
- 能否简化参数？
- 能否将更多复杂性隐藏在里面？

## 原则

- **深度是接口的属性，而非实现的属性。** 一个深度模块内部可以由小的、可 mock、可更换的部件组成——它们只是不属于接口。模块可以有**内部接缝（internal seams）**（对实现私有，由其自身测试使用）以及在接口处的**外部接缝（external seam）**。
- **删除测试。** 想象删除这个模块。如果复杂性消失了，它只是一个透传。如果复杂性重新出现在 N 个调用者中，说明它物有所值。
- **接口就是测试表面。** 调用者和测试跨越相同的 seam。如果你想要测试*越过*接口，模块的形状可能不对。
- **一个 adapter 意味着假设性的 seam。两个 adapter 意味着真正的 seam。** 除非有东西真正在 seam 两侧变化，否则不要引入 seam。

## 为可测试性而设计

好的接口使测试变得自然：

1. **接受依赖，不要创建它们。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面积。** 更少的方法 = 更少的测试需求。更少的参数 = 更简单的测试设置。

## 关系

- 一个 **Module** 恰好有一个 **Interface**（它呈现给调用者和测试的表面）。
- **Depth** 是一个 **Module** 的属性，对照其 **Interface** 衡量。
- **Seam** 是 **Module** 的 **Interface** 所在的位置。
- **Adapter** 位于 **Seam** 处并满足 **Interface**。
- **Depth** 为调用者产生 **Leverage**，为维护者产生 **Locality**。

## 被拒绝的框架

- **将深度作为实现行数与接口行数的比率**（Ousterhout）：奖励填充实现。我们改用 depth-as-leverage（深度即杠杆效应）。
- **"Interface"作为 TypeScript 的 `interface` 关键字或类的公共方法**：太窄——这里的 interface 包括调用者必须知道的每一个事实。
- **"Boundary"**：与 DDD 的有界上下文重载。说 **seam** 或 **interface**。

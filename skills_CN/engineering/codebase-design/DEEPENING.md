# 深化（Deepening）

如何在给定依赖关系的情况下安全地深化一组浅层模块。假设你已经熟悉 [SKILL.md](SKILL.md) 中的术语——**模块（module）**、**接口（interface）**、**接缝（seam）**、**适配器（adapter）**。

## 依赖分类

在评估一个模块是否适合深化时，先对其依赖进行分类。分类决定了深化后的模块如何跨接缝进行测试。

### 1. 进程内依赖（In-process）

纯计算、内存状态、无 I/O。始终可深化——直接合并模块并通过新接口进行测试。不需要适配器。

### 2. 本地可替代依赖（Local-substitutable）

具有本地测试替身的依赖（如 PGLite 替代 Postgres、内存文件系统）。如果替身存在，则可深化。深化后的模块在测试套件中使用替身运行。接缝是内部的；模块的外部接口处不需要端口（port）。

### 3. 远程但自有（端口与适配器模式，Ports & Adapters）

通过网络边界访问的自有服务（微服务、内部 API）。在接缝处定义一个**端口（port）**（即接口）。深化的模块拥有业务逻辑，传输层作为**适配器（adapter）**注入。测试使用内存适配器。生产环境使用 HTTP/gRPC/消息队列适配器。

推荐的表述形式：*"在接缝处定义一个端口，为生产环境实现 HTTP 适配器，为测试实现内存适配器，这样逻辑就可以集中在一个深层模块中，即使它被部署在网络上。"*

### 4. 真正的外部依赖（Mock）

你无法控制的第三方服务（如 Stripe、Twilio 等）。深化后的模块将外部依赖作为注入的端口接收；测试提供一个模拟适配器。

## 接缝纪律

- **一个适配器意味着假设性的接缝，两个适配器意味着真实的接缝。** 除非至少有两个适配器是合理的（通常是生产环境 + 测试），否则不要引入端口。单一适配器的接缝只是间接调用。
- **内部接缝 vs 外部接缝。** 一个深层模块可以同时拥有内部接缝（对其实现私有，仅供自身测试使用）以及接口处的外部接缝。不要因为测试使用了内部接缝，就把它们通过接口暴露出去。

## 测试策略：替换，而非叠加

- 一旦在深化模块的接口处编写了测试，旧的对浅层模块的单元测试就变成了浪费——删除它们。
- 在深化模块的接口处编写新测试。**接口就是测试的边界**。
- 测试通过接口断言可观察的结果，而非内部状态。
- 测试应该能够承受内部重构——它们描述的是行为，而不是实现。如果实现改变时测试也必须改变，说明测试越过了接口边界。

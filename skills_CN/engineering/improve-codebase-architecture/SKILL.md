# 改进代码库架构

发现架构摩擦并提议 **deepening opportunities（深化机会）**——将浅模块（shallow module）转变为深模块（deep module）的重构。目标是可测试性和 AI 可导航性。

此命令受项目的领域模型驱动，并建立在共享的设计词汇之上：

- 运行 `/codebase-design` skill 获取架构词汇（**module（模块）**、**interface（接口）**、**depth（深度）**、**seam（接缝）**、**adapter（适配器）**、**leverage（杠杆效应）**、**locality（局部性）**）及其原则（删除测试、"接口即测试面"、"一个 adapter = 假设性 seam，两个 = 真实的 seam"）。在每个建议中精确使用这些术语——不要偏离到"component"、"service"、"API"或"boundary"。
- `CONTEXT.md` 中的领域语言为良好的 seam 提供了名称；`docs/adr/` 中的 ADR（架构决策记录）记录了此命令不应重新讨论的决策。

## 流程

### 1. 探索

**先确定范围再扫描——YAGNI。** 深化一个模块的回报在于使未来对该模块的修改更容易，因此应重点关注最近发生变化的代码库部分。在查看之前先决定*在哪里*查看：

- 如果用户指定了方向——一个模块、一个子系统、一个痛点——接受它，并跳过下面的推断。
- 否则，回溯提交历史（`git log --oneline`）中的一段较长时间，找到代码库的热点——反复出现的文件和区域——并让这些路径首先吸引你的注意力。如果更改分散且没有明确的热点，扩大搜索范围。

首先阅读项目的领域词汇表（`CONTEXT.md`）以及你将要触及区域中的任何 ADR。

然后派生一个子智能体来浏览代码库。不要遵循僵化的启发式规则——有机地探索，并记录你在哪里遇到摩擦：

- 在哪里理解一个概念需要在许多小模块之间来回跳转？
- 哪些模块是**浅的**——接口几乎和实现一样复杂？
- 哪些纯函数仅仅为了可测试性而被提取出来，但真正的 bug 隐藏在它们的调用方式中（没有**局部性**）？
- 哪些紧密耦合的模块在其 seam 处泄漏？
- 代码库的哪些部分未经测试，或者难以通过其当前接口进行测试？

将**删除测试**应用于任何你怀疑是浅层的东西：删除它会集中复杂性，还是仅仅移动它？"是的，会集中"就是你想要的信号。

### 2. 将候选方案呈现为 HTML 报告

编写一个自包含的 HTML 文件到操作系统临时目录，这样不会在仓库中留下任何文件。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（在 Windows 上为 `%TEMP%`），并写入 `<tmpdir>/architecture-review-<timestamp>.html`，以便每次运行都获得一个新文件。为用户打开它——在 Linux 上使用 `xdg-open <path>`，在 macOS 上使用 `open <path>`，在 Windows 上使用 `start <path>`——并告知用户绝对路径。

报告使用 **通过 CDN 加载的 Tailwind** 进行布局和样式设计，以及 **通过 CDN 加载的 Mermaid** 来绘制图表，在图形/流程/序列能可靠传达结构的地方使用。将 Mermaid 与手工制作的 CSS/SVG 视觉元素混合——当关系是图形化的（调用图、依赖关系、序列）时使用 Mermaid，当你想要更具编辑性（质量图、剖面图、折叠动画）时使用手工构建的 div/SVG。每个候选方案都获得一个**前后对比可视化**。要注重视觉效果。

对于每个候选方案，渲染一张卡片，包含：

- **文件**——涉及哪些文件/模块
- **问题**——当前架构为何引起摩擦
- **解决方案**——用通俗中文描述将会发生什么变化
- **收益**——用局部性和杠杆效应来解释，以及测试将如何改进
- **前后对比图**——并排、自定义绘制，说明浅层性和深化效果
- **推荐强度**——`Strong（强烈推荐）`、`Worth exploring（值得探索）`、`Speculative（探索性的）`之一，渲染为徽章

在报告末尾添加一个**首选推荐**部分：你会先处理哪个候选方案以及原因。

**对领域使用 CONTEXT.md 的词汇，对架构使用 /codebase-design 的词汇。** 如果 `CONTEXT.md` 定义了"Order"，就谈论"the Order intake module（订单接收模块）"——而不是"the FooBarHandler"，也不是"the Order service"。

**ADR 冲突**：如果一个候选方案与现有的 ADR 冲突，只有当摩擦真实到足以值得重新审视该 ADR 时才提出来。在卡片中清晰标记（例如警告标注：_"与 ADR-0007 冲突——但值得重新讨论，因为……"_）。不要列出每个理论上被 ADR 禁止的重构。

参见 [HTML-REPORT.md](HTML-REPORT.md) 了解完整的 HTML 脚手架、图表模式和样式指南。

**不要**在此时提议接口。文件写入后，询问用户："你想探索这些中的哪一个？"

### 3. 深入探讨循环

一旦用户选择了候选方案，运行 `/grilling` skill 与他们一起走决策树——约束条件、依赖关系、深化后的模块形态、seam 后面是什么、哪些测试能保留。

随着决策的明确，副作用会在线发生——运行 `/domain-modeling` skill 来保持领域模型的最新状态：

- **将一个深化模块命名为 `CONTEXT.md` 中不存在的概念？** 将该术语添加到 `CONTEXT.md` 中。如果文件不存在则惰性创建。
- **在对话过程中澄清了一个模糊的术语？** 立即更新 `CONTEXT.md`。
- **用户因关键性原因拒绝了候选方案？** 提供一个 ADR，表述为："_希望我将此记录为 ADR，以便未来的架构审查不再重新建议它吗？_" 只有当该原因确实会被未来的探索者用来避免重复建议时才提供——跳过一时的原因（"现在不值得"）和不言自明的原因。
- **想要探索深化模块的替代接口？** 运行 `/codebase-design` skill 并使用其"设计两次"的并行子代理模式。

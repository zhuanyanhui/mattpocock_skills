对 `HEAD` 与用户提供的固定点之间的 diff 进行双轴审查：

- **标准（Standards）** — 代码是否符合本仓库记录的编码标准？
- **规格（Spec）** — 代码是否忠实地实现了发起的 issue / spec？

两个轴都作为**并行子 agent** 运行，以免污染彼此的上下文，然后此 skill 汇总它们的发现。

Issue 跟踪器应该已经提供给你——如果 `docs/agents/issue-tracker.md` 缺失，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 确定固定点

用户所说的任何固定点——commit SHA、分支名、tag、`main`、`HEAD~5` 等。如果用户没有指定，询问。

一次性捕获 diff 命令：`git diff <fixed-point>...HEAD`（三点语法，这样比较的是与 merge-base 的差异）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录 commit 列表。

在继续之前，确认固定点能解析（`git rev-parse <fixed-point>`）且 diff 非空。错误的引用或空的 diff 应该在这里失败——而不是在两个并行子 agent 内部。

### 2. 识别规格来源

按此顺序查找原始规格：

1. commit 消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）——通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传递的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的 spec 文件。
4. 如果未找到任何内容，询问用户规格在哪里。如果他们说没有规格，**Spec** 子 agent 将跳过并报告"无规格可用"。

### 3. 识别标准来源

仓库中记录了应如何编写代码的任何内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了仓库记录的内容外，标准轴始终携带下面的**气味基线（smell baseline）**——一组固定的 Fowler 代码坏味（_Refactoring_，第 3 章），即使仓库没有记录任何约定也适用。两条规则约束它：

- **仓库覆盖。** 记录的仓库标准总是优先；如果它认可了基线会标记的内容，则压制该气味。
- **始终是判断。** 每个气味都是一个带标签的启发式（"可能的 Feature Envy"），而非硬性违规——并且，和这里的任何标准一样，跳过工具已强制执行的内容。

每个气味描述*它是什么*→*如何修复*；与 diff 进行匹配：

- **Mysterious Name（神秘命名）** — 一个函数、变量或类型，其名称不揭示其功能或含义。→ 重命名；如果找不到合适的名称，说明设计不清晰。
- **Duplicated Code（重复代码）** — 相同的逻辑形状出现在变更中的多个 hunk 或文件中。→ 提取共享的形状，从两处调用。
- **Feature Envy（依恋情结）** — 一个方法访问另一个对象的数据多于自己的。→ 将该方法移动到它所依恋的数据上。
- **Data Clumps（数据泥团）** — 相同的几个字段或参数总是结伴出现（一个亟待诞生的类型）。→ 将它们捆绑成一个类型，传递该类型。
- **Primitive Obsession（基本类型偏执）** — 一个基本类型或字符串代替了应有自己类型的领域概念。→ 给该概念一个自己的小型类型。
- **Repeated Switches（重复的 switch）** — 相同的 `switch`/`if` 级联在相同类型上在变更中重复出现。→ 用多态替换，或使用两个站点共享的一个映射。
- **Shotgun Surgery（霰弹式修改）** — 一个逻辑变更迫使 diff 中许多文件分散编辑。→ 将一起变更的内容集中到一个模块中。
- **Divergent Change（发散式变更）** — 一个文件或模块因多个不相关的原因被编辑。→ 拆分，使每个模块因为一个原因变更。
- **Speculative Generality（夸夸其谈的未来性）** — 为 spec 没有的需求添加的抽象、参数或钩子。→ 删除它；内联回去，直到出现真正的需求。
- **Message Chains（消息链）** — 调用者不应依赖的长 `a.b().c().d()` 导航。→ 将遍历隐藏到第一个对象的一个方法后面。
- **Middle Man（中间人）** — 一个类或函数大部分只是委托转发。→ 删除它，直接调用真正的目标。
- **Refused Bequest（被拒绝的遗赠）** — 一个子类或实现忽略或重写其继承的大部分内容。→ 放弃继承，使用组合。

### 4. 并行生成两个子 agent

**标准子 agent 提示**——包含：

- 完整的 diff 命令和 commit 列表。
- 你在步骤 3 中找到的标准源文件列表，**加上步骤 3 中的气味基线**完整粘贴——子 agent 没有其他途径访问它。
- 简报："报告——在相关处按文件/hunk——(a) diff 违反已记录标准的每个地方：引用标准（文件 + 规则）；(b) 你发现的任何基线气味：命名它并引用 hunk。区分硬性违规与判断——已记录标准的违规可以是硬性的，但基线气味始终是判断，而已记录的仓库标准覆盖基线。跳过工具已强制执行的内容。不超过 400 字。"

**规格子 agent 提示**——包含：

- diff 命令和 commit 列表。
- spec 的路径或获取的内容。
- 简报："报告：(a) spec 要求但缺失或不完整的需求；(b) diff 中 spec 未要求的行为（范围蔓延）；(c) spec 要求已实现但实现看起来有误的需求。为每个发现引用 spec 行。不超过 400 字。"

如果 spec 缺失，跳过 Spec 子 agent 并在最终报告中注明。

### 5. 汇总

在 `## Standards` 和 `## Spec` 标题下呈现两份报告，逐字呈现或稍加清理。**不要**合并或重新排列发现——两个轴刻意保持独立（见_为什么是两个轴_）。

以一行摘要结束：每个轴的总发现数，以及每个轴内的最严重问题（如果有）。不要跨轴评判孰优孰劣——这正是分离存在的目的。

## 为什么是两个轴

一项变更可能通过一个轴而失败于另一个轴：

- 遵循所有标准但实现了错误的功能 → **标准通过，规格失败。**
- 完全按照 issue 要求做了但破坏了项目约定 → **规格通过，标准失败。**

分开报告可防止一个轴掩盖另一个轴。

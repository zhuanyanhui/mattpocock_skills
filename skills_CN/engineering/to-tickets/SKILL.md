# 转为工单

将计划、规范或对话拆分为一组**工单**——示踪弹垂直切片，每个工单声明**阻塞**它的其他工单。

问题跟踪器和分类标签词汇应该已经提供给你——如果没有，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话上下文中已有的内容开展工作。如果用户传入了引用（规范路径、问题编号或 URL）作为参数，获取它并阅读其完整正文和评论。

### 2. 探索代码库（可选）

如果你尚未探索代码库，请了解代码的当前状态。工单标题和描述应使用项目的领域词汇表，并尊重你所接触区域的 ADR。

寻找预重构的机会，使实现更容易。"先让变更变得容易，再做出容易的变更。"

### 3. 起草垂直切片

将工作拆分为**示踪弹**工单。

<vertical-slice-rules>

- 每个切片切出一个狭窄但**完整**的路径，贯穿每一层（schema、API、UI、测试）——是垂直的，而非某一层的水平切片
- 完成后的切片可独立演示或验证
- 每个切片的大小适合单个新的上下文窗口
- 任何预重构应首先完成

</vertical-slice-rules>

为每个工单指定其**阻塞边**——必须在其之前完成的其他工单。没有阻塞项的工单可以立即开始。

**大规模重构是垂直切片的例外。** **大规模重构**是一项机械性变更——重命名列、更改共享符号的类型——其**影响范围**遍布整个代码库，因此单个编辑会同时破坏数千个调用点，没有任何垂直切片能够保持绿色。不要强行将其塞入示踪弹；而是将其编排为**展开-收缩**序列。首先展开：在旧形式旁边添加新形式，这样不会破坏任何内容。然后按影响范围大小分批迁移调用点（按包、按目录），每批作为独立的工单，由展开步骤阻塞，由于旧形式仍然存在，每批之间保持 CI 绿色。最后收缩：在没有调用者后删除旧形式，作为一个由所有迁移批次阻塞的工单。即使分批后各批次无法独立保持绿色，也要保持该序列，但让它们共享一个集成分支，所有批次都阻塞一个最终的集成与验证工单——仅在该工单处承诺绿色。

### 4. 向用户提问

将建议的拆分方案以编号列表呈现。对于每个工单，显示：

- **标题**：简短描述性名称
- **被阻塞于**：哪些其他工单（如果有）必须首先完成
- **交付内容**：此工单实现的端到端行为

询问用户：

- 粒度是否合适？（太粗 / 太细）
- 阻塞边是否正确——每个工单是否只依赖真正阻塞它的工单？
- 是否有工单应该合并或进一步拆分？

不断迭代，直到用户批准拆分方案。

### 5. 将工单发布到已配置的跟踪器

发布已批准的工单。**具体方式**取决于 `/setup-matt-pocock-skills` 配置的跟踪器——工单内容相同，只有阻塞边的形式不同：

- **本地文件**→ 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下为每个工单写入一个文件，按依赖顺序从 `01` 开始编号（阻塞项在先）。每个文件的"被阻塞于"列出其所依赖的编号/标题。使用下面的单工单文件模板——每个文件一个工单，绝不能使用单个合并文件。
- **真实问题跟踪器（GitHub、Linear 等）**→ 按依赖顺序为每个工单发布一个问题（阻塞项在先），以便每个工单的阻塞边可以引用真实标识符。如果平台有原生的阻塞/子工单关系则使用它；否则在每个工单的"被阻塞于"中设置阻塞工单。应用 `ready-for-agent` 分类标签，除非另有指示——这些工单天然可被 agent 获取。

处理**前沿**：所有阻塞项都已完成的工单。对于纯线性链，意味着从上到下。

**不要**关闭或修改任何父问题。

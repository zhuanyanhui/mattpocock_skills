# Wizard

**wizard（向导脚本）**是一个 bash 脚本，逐步引导人类完成一个手动流程——那些亲手操作很繁琐、每次又很难向 AI 重新解释清楚的流程。它会打开每个 URL、精确说明该点击和复制什么、捕获返回值、写入正确位置（`.env`、GitHub secrets），在每个阶段确认进度，并显示还剩多少阶段。它可以用来配置第三方服务、执行一次性迁移，或把项目从一个状态迁移到另一个状态。

优秀的 UX 已经由 [template.sh](template.sh) 解决了——分阶段进度、确认关卡、跨平台 URL 打开（包括 WSL）、隐藏式密文输入、幂等的 `.env` upsert、`gh secret`/`gh variable` 写入，以及结束时的汇总。**你唯一的工作是确定流程范围并编写各个阶段。** `STAGES` 标记上方的库代码在每个 wizard 中都完全相同；这种一致性正是它的意义所在——永远不要手动编辑它。

wizard 默认是一次性的——为一次运行而生，保存到 scratch 或 `scripts/` 路径下，任务完成后删除。只有当用户希望将可重复的设置流程保留在仓库中时，才提交它。

## 流程

### 1. 确定流程范围

找出人类必须执行的每个手动步骤以及沿途捕获的每个值。先读仓库——不要冷启动提问：

- 对于设置类任务：`.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置和 `.github/workflows/*`（每个 `secrets.*` / `vars.*` 引用都是 wizard 必须产出的值）。
- 对于迁移或切换类任务：当前状态、目标状态，以及两者之间的不可逆操作。

然后向用户展示有序的阶段列表及各阶段产出的值，并确认——他们可能会增删或重排序。

**完成标志：** 每个阶段都已按序命名，且对于每个被捕获的值，你知道 (a) 人类从哪里获取它，(b) 它被写到哪里（`.env`、GitHub secret、两者都是、或无处可写——有些阶段只是纯动作），以及 (c) 它是密文（隐藏输入）还是明文。

### 2. 映射每个阶段的路径

对于每个阶段，写出人类遵循的精确路径：打开哪个 URL、在那里做什么、值在哪里显示、填入哪个变量——例如 "Dashboard → Developers → API keys → Reveal test key → 复制"。当你不知道当前的 UI 或确切命令时，如实说明并向用户确认或查阅文档——永远不要编造可能不存在的步骤。

**完成标志：** 每个阶段都能追溯到陌生人也能照做的具体指令。

### 3. 编写 wizard

将 `template.sh` 复制到目标路径。将示例阶段替换为每个步骤各一个 `stage`，按依赖顺序排列。使用库辅助函数——`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`——并将 `TOTAL_STAGES` 设置为你编写的阶段数。

以模板的水准要求自己：在要求输入值之前先打开 URL，对密文使用 `ask_secret`，对每个需要持久化的值使用 `write_env`，只对 CI 真正需要的值使用 `set_secret`，在任何不可逆操作前使用 `confirm`。每个 `stage` 会清屏，确保屏幕上只显示当前步骤——保持一个阶段只做一个聚焦的任务，这样人类需要的信息不会被滚走。不要触碰标记上方的库代码。

### 4. 验证并交付

- `bash -n <script>`；如果有 `shellcheck` 就运行它。
- `chmod +x <script>`。
- 不要自己完整运行一遍——它会打开浏览器并在人类输入处阻塞。改为静态追踪：步骤 1 中的每个值都被捕获并写到了步骤 1 指定的位置，且每个 `set_secret` 名称精确匹配 CI 中的 `secrets.*` 引用。
- 告诉用户如何运行它。如果是可重复的设置流程，将它提交到仓库并在 README 中引用，这样下一个人直接跑脚本而不是去问 AI。

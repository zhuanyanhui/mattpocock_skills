# ADR 格式

ADR（架构决策记录）存放在 `docs/adr/` 目录中，使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

懒创建 `docs/adr/` 目录——仅在需要第一个 ADR 时才创建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：背景是什么，我们做了什么决定，以及为什么。}
```

就这样。一个 ADR 可以只有一段话。价值在于记录*做出了一个决定*以及*为什么*——而不是填满各个章节。

## 可选章节

仅在这些内容能带来真正价值时才包含。大多数 ADR 不需要它们。

- **Status** 前置元数据（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——在决策可能被重新审视时有用
- **Considered Options**（考虑过的选项）——仅在被拒绝的替代方案值得记住时才列出
- **Consequences**（后果）——仅在有非显而易见的下游影响需要注明时才列出

## 编号

扫描 `docs/adr/` 目录中现有的最大编号，然后加一。

## 何时应该提供 ADR

必须同时满足以下三个条件：

1. **难以逆转**——以后改变主意的代价是有意义的
2. **缺乏上下文时会令人费解**——未来的读者看到代码时会想"他们到底为什么这么做？"
3. **真正权衡后的结果**——存在真正的替代方案，你出于特定原因选择了其中一个

如果一个决策很容易逆转，跳过它——你反正会逆转的。如果它不令人费解，没人会好奇原因。如果没有真正的替代方案，除了"我们做了显而易见的事"之外没什么可记录的。

### 符合 ADR 条件的情况

- **架构形态。** "我们使用 monorepo。" "写入模型是事件溯源的，读取模型被投影到 Postgres 中。"
- **上下文之间的集成模式。** "订单和计费通过领域事件通信，而非同步 HTTP。"
- **会带来锁定效应的技术选型。** 数据库、消息总线、认证提供商、部署目标。不是每个库都算——只有那些更换起来需要一个季度才能完成的才算。
- **边界和范围决策。** "客户数据由客户上下文拥有；其他上下文只能通过 ID 引用。" 明确的"不"与明确的"是"同样有价值。
- **刻意偏离显而易见的路径。** "我们使用手写 SQL 而不是 ORM，因为 X。" 任何合理读者会假设相反做法的决策。这些能阻止下一位工程师去"修复"一个刻意为之的设计。
- **代码中不可见的约束。** "由于合规要求，我们不能使用 AWS。" "响应时间必须在 200ms 以内，因为合作伙伴 API 有合约要求。"
- **被拒绝的替代方案，且拒绝理由并非显而易见。** 如果你考虑过 GraphQL 并出于微妙原因选择了 REST，记录下来——否则六个月后还会有人再提议 GraphQL。

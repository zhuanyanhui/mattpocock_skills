# Diagnosing Bugs

针对棘手 bug 的纪律。只有在有明确理由时才跳过各阶段。

在浏览代码库时，阅读 `CONTEXT.md`（如果存在）以获得相关模块的清晰心智模型，并检查你所接触区域中的 ADR。

## Redact

此技能会展示命令、输出和捕获的产物。**先遮蔽所有秘密**——用 `<REDACTED>` 替代。构建循环时针对环境变量，这样凭据保留在环境中而非你展示的内容里。捕获的产物携带认证头：只引用携带信号的行。

如果遮蔽后的输出不足以诊断 bug，请说明并询问用户。

## 阶段 1 — 构建反馈循环

**这个技能就是它。** 其他一切都是机械性的。如果你有一个针对该 bug 的**紧**通过/失败信号——一个能在*这个* bug 上变红的信号——你就会找到原因；二分查找、假设检验和仪表化都只是消耗它。如果你没有这样一个信号，盯着代码看再多也没用。

在此投入不成比例的精力。**要积极。要有创意。拒绝放弃。**

### 构建反馈循环的方法——大致按此顺序尝试

1. **失败的测试**——在接触 bug 的任何 seam 处，单元、集成或端到端。
2. **Curl / HTTP 脚本**——针对正在运行的开发服务器。
3. **CLI 调用**——用 fixture 输入，将 stdout 与已知良好快照进行 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，在 DOM/控制台/网络上断言。
5. **回放捕获的追踪。** 将真实的网络请求/负载/事件日志保存到磁盘；通过代码路径在隔离中回放。
6. **一次性测试工具（throwaway harness）。** 启动系统的最小子集（一个服务，mock 依赖），通过单个函数调用执行 bug 代码路径。
7. **属性/模糊循环。** 如果 bug 是"有时输出错误"，运行 1000 个随机输入并查找失败模式。
8. **二分测试工具（bisection harness）。** 如果 bug 出现在两个已知状态（commit、数据集、版本）之间，自动化"在状态 X 启动、检查、重复"，这样你就可以 `git bisect run` 它。
9. **差异循环。** 通过旧版本与新版本（或两种配置）运行相同的输入，并对输出进行 diff。
10. **人机循环 bash 脚本。** 最后手段。如果必须由人点击，用 `scripts/hitl-loop.template.sh` *驱动*他们，使循环仍然有结构。捕获的输出反馈给你。

构建正确的反馈循环，bug 就 90% 修复了。

### 收紧循环

将循环视为产品。一旦你有了*一个*循环，**收紧**它：

- 能更快吗？（缓存设置，跳过不相关的初始化，缩小测试范围。）
- 能让信号更尖锐吗？（针对具体症状断言，而非"没有崩溃"。）
- 能更确定吗？（固定时间，播种 RNG，隔离文件系统，冻结网络。）

一个 30 秒的不稳定循环比没有好不了多少；一个 2 秒的确定性循环才是紧的——调试的超能力。

### 非确定性 bug

目标不是稳定的复现而是**更高的复现率**。循环触发 100 次，并行化，增加压力，缩小时间窗口，注入 sleep。50% 概率出现的 bug 是可以调试的；1% 则不行——持续提高复现率直到可以调试。

### 当你确实无法构建循环时

停下来并明确说明。列出你尝试过的方法。请求用户提供：(a) 访问能复现它的环境，(b) 已遮蔽的捕获产物（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或 (c) 添加临时生产仪表化的权限。**在拥有循环之前不要继续推测。**

### 完成标准——一个能变红的紧循环

阶段 1 完成的条件是循环**紧（tight）** 且**能变红（red-capable）**：你能命名**一个命令**——一个脚本路径、测试调用、curl——你已经**至少运行过一次**（展示调用及其输出，已遮蔽），并且它满足：

- [ ] **能变红（Red-capable）**——它驱动实际的 bug 代码路径，并断言**用户的确切症状**，所以它可以在这个 bug 上变红，修复后变绿。不是"无错误运行"——它必须能够*捕获这个特定的 bug*。
- [ ] **确定性（Deterministic）**——每次运行结果相同（不稳定 bug：固定的、高复现率，按前述）。
- [ ] **快速（Fast）**——秒级，不是分钟级。
- [ ] **可 agent 运行（Agent-runnable）**——你可以无人值守运行；仅通过 `scripts/hitl-loop.template.sh` 让人参与循环。

如果你发现自己在构建这个命令之前就开始阅读代码构建理论，**停下来——直接跳到假设正是这个技能要防止的确切失败。** 没有能变红的命令，就没有阶段 2。

## 阶段 2 — 复现 + 最小化

运行循环。观察它变红——bug 出现了。

确认：

- [ ] 循环产生了**用户**描述的失败模式——而不是恰好附近的一个不同失败。错误的 bug = 错误的修复。
- [ ] 失败在多次运行中可复现（或者，对于非确定性 bug，以足够高的复现率可调试）。
- [ ] 你已经捕获了确切的症状（错误消息、错误输出、缓慢的时间），以便后续阶段可以验证修复是否确实解决了它。

### 最小化

一旦变红，将复现缩小到**仍然能变红的最小场景**。一次**一个**地削减输入、调用者、配置、数据和步骤，每次削减后重新运行循环——只保留对失败有支撑作用的内容。

为什么费心：最小化复现缩小了阶段 3 中的假设空间（让人怀疑的移动部件更少），并成为阶段 5 中干净的回归测试。

完成时**每个剩余元素都是支撑性的**——移除任何一个都会使循环变绿。

在完成复现**并**最小化之前不要继续。

## 阶段 3 — 假设

在测试任何假设之前生成 **3-5 个排名假设**。单一假设生成会锚定在第一个看似合理的想法上。

每个假设必须是**可证伪的**：陈述它所做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会使 bug 消失 / <改变 Z> 会使 bug 更严重。"

如果你无法陈述预测，那么这个假设只是一种直觉——放弃它或打磨它。

**在测试之前向用户展示排名列表。** 他们通常拥有领域知识，可以立即重新排名（"我们刚刚部署了对 #3 的改动"），或知道他们已经排除的假设。廉价的检查点，巨大的时间节省。不要阻塞——如果用户不在，继续使用你的排名。

## 阶段 4 — 仪表化

每个探测必须映射到阶段 3 中的特定预测。**一次只改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查**——如果环境支持。一个断点胜过十条日志。
2. **目标化日志**——在区分假设的边界处。
3. 绝不"记录一切然后 grep"。

**在每个调试日志上标记唯一前缀**，例如 `[DEBUG-a4f2]`。结束时的清理变成一个单一的 grep。未标记的日志保留；已标记的日志删除。

**性能分支。** 对于性能回归，日志通常不合适。而是：建立基线测量（计时工具、`performance.now()`、分析器、查询计划），然后二分查找。先测量，后修复。

## 阶段 5 — 修复 + 回归测试

**在修复之前**编写回归测试——但前提是存在一个**正确的 seam**。

正确的 seam 是指测试能在调用点处执行**真实 bug 模式**的 seam。如果唯一可用的 seam 太浅（bug 需要多个调用者时的单调用者测试，无法复制触发 bug 的链的单元测试），在那里的回归测试会给出虚假的信心。

**如果没有正确的 seam 存在，那本身就是发现。** 记录下来。代码库架构阻止了 bug 被锁定。将此标记给下一阶段。

如果存在正确的 seam：

1. 将最小化的复现转化为在该 seam 处的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 针对原始（未最小化）场景重新运行阶段 1 的反馈循环。

## 阶段 6 — 清理 + 事后分析

在声明完成之前必须完成：

- [ ] 原始复现不再复现（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或 seam 缺失已记录在案）
- [ ] 所有 `[DEBUG-...]` 仪表化已移除（`grep` 前缀）
- [ ] 一次性原型已删除（或移至明确标记的调试位置）
- [ ] 证明正确的假设已记录在 commit / PR 消息中——这样下一个调试者可以学习

**然后问：什么本来可以防止这个 bug？** 如果答案涉及架构变更（没有好的测试 seam、混乱的调用者、隐藏的耦合），将具体细节移交给 `/improve-codebase-architecture` 技能。在修复**之后**而非之前提出建议——你现在拥有的信息比开始时更多。

# 原型

原型是**回答一个问题的一次性代码**。问题决定了形态。

## 选择分支

确定正在回答哪个问题——从用户的提示、周围的代码，或通过询问用户（如果用户在线）：

- **"这个逻辑/状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个可共享的单一 HTML 文件——自由操作按钮加分步引导 walkthrough——推动状态机通过那些在纸上难以推理的案例，非开发者也能操作。
- **"这应该看起来像什么？"** → [UI.md](UI.md)。在单个路由上生成几个截然不同的 UI 变体，可通过 URL 搜索参数和浮动底部栏切换。

两个分支产生非常不同的产物——选错了分支会浪费整个原型。如果问题确实模棱两可且用户无法联系到，默认选择与周围代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明该假设。

## 两者都适用的规则

1. **从第一天起就是一次性的，并明确标记。** 将原型代码放在实际使用位置附近（在它正在为其制作原型的模块或页面旁边），以便上下文显而易见——但要命名得让随便一看的人能看出是原型而不是生产代码。对于一次性 UI 路由，遵循项目已有的任何路由约定；不要发明新的顶层结构。
2. **易于运行。** UI 原型从项目任务运行器中的一条命令启动——`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑 demo 是一个用户双击即可打开的单一 HTML 文件。两种方式都无需思考即可启动。
3. **默认无持久化。** 状态存在于内存中。持久化是原型*正在验证*的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，访问一个临时数据库或本地文件，并带有明确的 "PROTOTYPE — wipe me" 名称。
4. **跳过打磨。** 没有测试，没有超出使原型*可运行*所需的错误处理，没有抽象。目标是快速获取信息。
5. **展现状态。** 在每个动作之后（逻辑）或每个变体切换时（UI），打印或渲染完整的相关状态，以便用户可以看到发生了什么变化。
6. **完成后保存。** 将任何验证通过的决策整合到真实代码中，然后将原型本身作为**一手资料**保存：将其提交到一个一次性分支上（不在 main 分支），并在实现 issue 上留下指向该分支的上下文指针。同时保存答案——结论及其解决的问题——在 issue 或提交中。main 分支只保留经过验证的决策。

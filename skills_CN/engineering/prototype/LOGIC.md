# 逻辑原型

一个自包含的单一 HTML 文件——一个**可共享的 demo**——让任何人通过点击按钮来驱动状态模型。当问题涉及**业务逻辑、状态转换或数据结构**时使用——这类东西纸上看着合理，但只有用真实案例跑过才能感觉出不对劲。

因为它是单个文件、无需安装任何东西，你可以把它交给非开发者——设计师、产品经理、领域专家——让他们亲自感受这个模型。所以它要说他们的语言，而不是代码的语言。

## 何时适用

- "我不确定这个状态机是否能处理 X 然后 Y 的边界情况。"
- "这个数据模型真的能让我表示那种情况吗……"
- "我想在实际编写之前感受一下 API 应该长什么样。"
- 任何**有人想要按下按钮、观察状态变化**的场景。

如果问题是"这个应该长什么样"——走错分支了。使用 [UI.md](UI.md)。

## 流程

### 1. 明确问题

在写代码之前，先写下你要原型化的状态模型和问题是什么。一段话，写在 demo 的顶部（在可见的介绍中，不仅仅是一行注释）。回答错误问题的逻辑原型纯属浪费——把问题明确写出来，以便后续核查，无论用户当时在场还是离开后回看。

### 2. 将逻辑隔离到可移植模块中

将实际逻辑——回答问题的核心部分——放在一个单一 `<script>` 块中，写成小型、纯的模块，以便日后可以提取并放入真实代码库。周围的页面是一次性的；这个模块不应该是。

合适的形态取决于问题：

- **纯 reducer**——`(state, action) => state`。适用于动作是离散事件、状态是单一值的场景。
- **状态机**——显式状态和转换。适用于"当前哪些动作甚至合法"本身就是问题的一部分时。
- **一组纯函数**作用于普通数据类型。适用于没有隐式当前状态——只有变换的场景。
- **具有清晰方法表面的类或模块**，当逻辑确实拥有持续的内部状态时。

选择最匹配所提问题的形态，*而非*最容易对接页面的形态。保持纯净：无 DOM、无 `document`、无按钮处理器伸进它内部。页面调用它；没有反向流动。这才是让原型在其生命周期之后仍有价值的关键：当问题有了答案，经过验证的 reducer / 状态机 / 函数集可以独立提取到真实模块中。

### 3. 构建可共享的 HTML 文件

一个文件，纯 HTML/CSS/JS——无框架、无打包、无服务器，全部内联，双击即可打开，甚至可以邮件发送。任何人都应该能通过打开它来运行。

为**非开发者**而写。每个标签都是**领域语言**，不是代码——按钮和状态读起来像业务，不像 reducer。用通俗的话解释发生了什么。

以清晰的层次布局，从上到下：

1. **标题和一行解释**——这个 demo 让你探索什么问题（来自步骤 1）。
2. **当前状态**——完整的相关状态，渲染为可读面板（带标签的字段，不是原始 JSON 转储），每次点击后重新渲染以便看到变化。在有助于非开发者理解时，注明刚刚发生了什么变化。
3. **自由操作按钮**——每个动作一个按钮，始终可用，任何人都可以按任何顺序摆弄模型。每次点击分派动作并重新渲染状态。
4. **引导式 walkthrough**——一组**场景**，每个一个标签页。每个标签页包含一段通俗语言描述的场景——它设置的情境和要观察的内容——以及下面按顺序排列的**要按的按钮**。每一步都是一个真正的按钮：点击它执行该动作并进入下一步。开始一个 walkthrough 时会重置到已知的初始状态，这样每次运行的场景都一样。

选择能演示尴尬情况的场景——正常路径、棘手的边界情况、尝试某件应该不合法的事情——那些在纸上难以推理的场景。

保持美观但克制：干净的排版、宽松的间距、一个强调色。无动画、无噱头——没有与状态和按钮争抢注意力的东西。

### 4. 交给用户

把文件发给他们，或为他们打开。他们会随时点击 walkthrough 和自由操作；有趣的时刻是他们说"等等，这不应该发生"或"咦，我以为 X 会不一样"的时候——这些正是 _想法_ 中的 bug，而这才是原型的意义所在。如果他们想要新动作或新场景，就添加。原型是不断演化的。

### 5. 记录答案并归档原型

原型回答完问题后，先记录答案，再按照 [SKILL](SKILL.md) 描述的方式归档原型。逻辑特定的映射：经过验证的 reducer / 状态机 / 函数集提取到真实模块（决策已吸收）；HTML 外壳随原型一起移至废弃分支，保留原型作为一手资料——而且因为它是自包含的单一文件，在那里也仍然可以轻易重新运行。

## 反模式

- **不要添加测试。** 需要测试的原型已经不是原型了。
- **不要对接真实数据库。** 使用内存状态，除非问题明确与持久化相关。
- **不要泛化。** 不要考虑"如果以后想支持 X 怎么办"。原型只回答一个问题。
- **不要把逻辑和页面混在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理器，就不再可提取了。保持页面作为纯模块之上的薄壳。
- **不要使用框架、打包器或服务器。** 接收者双击即可运行的单一文件；React 应用或开发服务器会毁掉"可共享"。
- **不要把 HTML 外壳发布到生产环境。** 页面是为手动点击而优化的。其背后的逻辑模块才是值得保留的部分。

# UI 原型

生成**多个截然不同的 UI 变体**，通过悬浮底部栏切换。用户在浏览器中翻转各变体，选择一个（或从每个中抽取优点），然后扔掉其余的。

如果问题是关于逻辑/状态而非外观——走错分支了。使用 [LOGIC.md](LOGIC.md)。

## 何时适用

- "这个页面应该长什么样？"
- "我想在确定之前看看这个仪表板的几个选项。"
- "试试设置页面的不同布局。"
- 任何用户本可以花一整天在脑海中三个模糊草稿之间做选择的场景。

## 两种子形态——强烈优先子形态 A

当 UI 原型**紧贴应用其余部分**时更容易判断——真实的头部、真实的侧边栏、真实的数据、真实的密度。一个孤立的废弃路由是真空状态：每个变体单独看都没问题。只要有合理的现有页面可以承载变体，就默认使用子形态 A。只有在原型确实没有就近可放之处时，才选择子形态 B。

### 子形态 A —— 对现有页面的调整（首选）

路由已存在。变体在**同一路由**上渲染，由 `?variant=` URL 搜索参数控制。现有的数据获取、参数和认证全部保留——只有渲染部分切换。这是默认选择，除非有特定理由否则选它。

如果原型针对的还没有页面，但*自然会归属于某个页面*（仪表板的新区域、设置页面的新卡片、现有流程的新步骤）——那也仍是子形态 A。在宿主页面内挂载各变体。

### 子形态 B —— 新页面（最后手段）

仅当被原型化的东西确实没有现有页面可以归属时才使用——例如一个全新的顶级表面，或无法嵌入任何合理位置的流程。

按照项目已有的路由约定创建一个**废弃路由**——不要发明新的顶级结构。命名要让人一眼看出是原型（例如路径或文件名中包含 `prototype`）。同样使用 `?variant=` 模式。

在确定子形态 B 之前，先做一次健全性检查：真的没有可以嵌入的现有页面吗？空路由会掩盖有真实内容的页面会暴露的设计问题。

在两种子形态中，底部悬浮栏都是相同的。

## 流程

### 1. 明确问题并确定 N

默认为 **3 个变体**。超过 5 个就不再是截然不同的变体，而变成噪音了——上限就是 5。

用一行写下计划，放在原型位置或文件顶部注释中：

> "Three variants of the settings page, switchable via `?variant=`, on the existing `/settings` route."

无论用户是否想提出异议，这种方式都适用。

### 2. 生成截然不同的变体

起草每个变体。每个都要符合：

- 页面的目的和可访问的数据。
- 项目的组件库/样式系统（TailwindCSS、shadcn、MUI、纯 CSS 等）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

各变体必须**结构性不同**——不同的布局、不同的信息层次、不同的主要交互方式，而不仅仅是不同的颜色。三个微调过的卡片网格不是 UI 原型，那是壁纸。如果两个草稿太相似，用明确的"不要使用卡片网格"指引重做其中一个。

### 3. 将它们连接起来

在路由上创建一个统一的切换组件：

```tsx
// pseudo-code — adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形态 A（现有页面）：在切换器上方保留所有现有的数据获取逻辑；只有渲染的子树随变体切换。

对于子形态 B（新页面）：`/prototype/<name>` 下的废弃路由挂载同样的切换器。

### 4. 构建悬浮切换栏

屏幕底部中央的一个小型固定定位栏，包含三个部分：

- **左箭头**——切换到上一个变体（循环）。
- **变体标签**——显示当前变体键值，如果变体导出了名称则一并显示。例如 `B — Sidebar layout`。
- **右箭头**——切换到下一个变体（循环）。

行为：

- 点击箭头更新 URL 搜索参数（使用框架的路由器——Next 用 `router.replace`，React Router 用 `navigate` 等），使变体可分享且在刷新后保持稳定。
- 键盘：`←` 和 `→` 箭头键也可切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时不要拦截箭头键。
- 与页面视觉上有明显区别（例如高对比度药丸形状、微妙阴影），让人一眼看出它不属于被评估的设计。
- 在生产构建中隐藏——用 `process.env.NODE_ENV !== 'production'` 或等价检查来门控，这样意外合并的原型不会将栏发布给用户。

将切换器放在一个共享组件中，以便两种子形态都可以复用。放置在项目中共享 UI 所在的位置。

### 5. 交给用户

提供 URL（以及 `?variant=` 键值）。用户可以在方便时翻转浏览。通常有趣的反馈是 **"我想要 B 的头部搭配 C 的侧边栏"**——这才是他们真正想要的设计。

### 6. 记录答案并清理

当一个变体胜出后，记录答案——哪个变体以及原因——然后按照 [SKILL](SKILL.md) 描述的方式归档原型。将胜者折叠进真实代码，其余移到废弃分支，而非主分支：

- **子形态 A**——将胜者折叠进现有页面；从主分支中删除失败的变体和切换器。
- **子形态 B**——将胜出变体提升为真实路由；从主分支中删除废弃路由和切换器。

完整的变体集合是一手资料，所以它落在废弃分支上而不是垃圾桶里——留在主分支中的变体组件和切换器会很快腐化并让下一个读者困惑。

## 反模式

- **只在颜色或文案上有差异的变体。** 那是微调，不是原型。真正的变体在结构上有分歧。
- **在变体之间共享过多代码。** 共享 `<Header>` 没问题；共享 `<Layout>` 则违背了目的。每个变体应能自由抛弃布局。
- **将变体对接真实变更操作。** 只读原型就可以了。如果变体需要变更操作，指向一个 stub——问题是"这应该长什么样"，而不是"后端能否工作"。
- **直接将原型发布到生产环境。** 变体代码是在原型约束下编写的（无测试、极少的错误处理）。在折叠进正式代码时应正确重写。

用户要求进行一次**回顾**（retrospective）。你要为编码 agent 的**环境**提出改进建议，以改善未来的运行。

## 步骤

1. 调用 Skill 工具加载 `writing-for-agents`，获取写作风格指南。

2. 阅读用户指定会话的一手资料。这可能意味着要在本机的会话日志中搜索。如果用户没有指定会话，默认使用当前会话。

3. 在以下类别中寻找可改进的候选点。

- **导航**：agent 找到正确文件有多容易？文件之间是否存在隐藏依赖？一个**导航指针**能否让它更容易？_当_会话花费很长时间才找到某条信息时使用。
- **自动化检查**：是否有能捕获 agent 所犯错误的自动化检查？Linting、类型检查、测试、文件系统 linter？先阅读仓库自己的检查命令（它的 `package.json`/构建工具的 `lint`/`check` 脚本、它的 CI 工作流），这样如果某个检查已经存在却未被接入或已静默失效，那就是发现，而不是重新发明。一个没有**护栏**（既没有 pre-commit 钩子，也没有运行其 lint/typecheck/test 命令的 CI 任务）的仓库本身就是一个发现：未做 lint 的仓库是一个持续错失的机会，而不是中性的默认状态。_当_agent 犯了本可被自动化检查捕获的错误，或仓库根本没有护栏时使用。
- **编码标准**：是否应该给**审查 agent** 一条新规则去执行？是否应删除或澄清现有规则？先对违规分类：**机械性**违规（固定的语法模式、被禁用的 API、import 形态、文件位置规则）就做确定性检查，仅此而已：仓库自有 linter 中的自定义规则、新的 pre-commit 钩子，或新的 CI 任务——取决于仓库的语言和现有护栏，哪种最便宜就用哪种。默认选择构建检查而非编写规则。`CODING_STANDARDS.md` 只留给真正的**判断性意见**（跨文件一致性、"与周边风格匹配"、任何护栏永远无法替代的情况）。_当_审查 agent 未能捕获错误时使用。
- **全局 AGENTS.md**：是否有任何引导指令应该改为移到编码标准（或自动化检查）中？_当_AGENTS.md 文件特别大时使用——无论是在仓库中还是在用户的全局作用域中。
- **工具经济性**：agent 是否发出了本可精简的昂贵工具调用？是否有任何自定义工具（CLI、MCP）特别耗费 token？_当_agent 发出了昂贵的工具调用时使用。
- **无操作指令**：在引导文件中寻找不会改变 agent 行为的指令。_当_引导文件庞大且笨重时使用。
- **信息获取**：寻找增加 agent 信息获取机会的途径。将 dev server 日志分流（tee）到文件、对第三方服务的只读访问。_当_某条关键信息对 agent 不可用时使用。

4. 按严重程度顺序向用户呈现这些候选点。

## 参考

### 实现 vs 审查

记住所有工作都经过两个阶段：实现和审查。实现 agent 承受最大的**上下文压力**。它负责探索、编写代码和调试失败。

审查 agent 的上下文压力最小——它接收一个 diff，因此无需探索。它通常不需要编写代码或调试。

这意味着应该由审查 agent 负责施加编码标准，而不是实现 agent。

### 文件

你可以访问仓库中的若干文件：

- `CLAUDE.md`/`AGENTS.md`：这些文件会被推送到在此仓库中工作的任何 agent 的上下文窗口。它们应极其节制地使用，通常只用于指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：此文件在审查时读取，而非实现时。如果标准文件超过 1,000 行，请添加指向 docs 文件夹的**导航指针**。
- Docs：将 docs 用作参考文件，由其他文件指向。在编写新文档前先寻找现有文档。
- Skills：将 skills 用于文档（因为它们的 description 会进入 agent 的上下文窗口），或用于用户调用的命令。遵循 `writing-for-agents` skill 中的建议。

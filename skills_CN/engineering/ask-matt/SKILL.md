# Ask Matt

你记不住所有技能，所以直接问。

一个 **flow（流程）** 是贯穿各技能的一条路径。大多数路径沿着一条 **主流程（main flow）** 展开，两条 **入口匝道（on-ramp）** 汇入其中。其余的都是独立技能，或在其他技能之下运行的词汇层。

## 主流程：构思 → 交付

大多数工作行进的路线。你有一个想法，想要把它构建出来。

1. **`/grill-with-docs`** — 通过访谈打磨想法。当你**有一个工作目录**时从这里开始：它是有状态的，会将所学内容保留在 `CONTEXT.md` 和 ADR 中。（没有工作目录？使用 `/grill-me`——参见独立技能。两者都运行相同的 `/grilling` 原语；`grill-with-docs` 是留下文档记录的那个，这使得它比两者中更好——只要有一个仓库可以存放这些记录。）
2. **分支——你能在对话中解决所有问题吗？** 如果某个问题需要可运行的答案（状态、业务逻辑、必须看到的 UI），则绕道通过 prototype，由 **`/handoff`** 在两侧桥接（一个 prototype 存放在它自己的目录中——这正是 `/handoff` 的用途——参见阶段边界）：
   - **`/handoff`** 传出，然后针对该文件打开一个全新会话，
   - **`/prototype`** 用一次性代码回答问题，
   - **`/handoff`** 传回你学到的东西，并在原始构思线程中引用它。
3. **分支——这是多会话构建吗？**
   - **是** → **`/to-spec`**（将线程转化为 spec），然后 **`/to-tickets`** 将其拆分为 tracer-bullet（示踪弹）任务，每个任务声明其 **阻塞边（blocking edges）**。在本地跟踪器上，每个任务是一个文件，位于 `.scratch/<feature>/issues/` 下，按阻塞优先手动处理；在真实跟踪器上，边成为原生阻塞链接，因此任何阻塞项已完成的任务都可以被领取——对每个任务启动 **`/implement`**，**在每个任务之间用 `/clear` 清除上下文**。每个任务都是自包含的，所以最后一个任务的上下文可以丢弃。
   - **否** → 直接在同一个上下文窗口中执行 **`/implement`**。

   无论哪种方式，**`/implement`** 都通过在内部驱动 **`/tdd`** 来构建每个 issue——一次一个红-绿切片——然后在提交前运行 **`/code-review`**，对 diff 进行双轴审查（标准 + 规格）。当你只想在没有完整 spec 的情况下以测试优先的方式构建具体行为时，单独使用 **`/tdd`**；当你想要针对固定点审查分支或 PR 时，单独使用 **`/code-review`**。

### 上下文卫生

保持步骤 1-3 在**一个不间断的上下文窗口**中——在 `/to-tickets` 之前不要压缩或清除——这样审查、spec 和任务都建立在相同的思考基础上。然后每个 `/implement` 从任务开始，重新启动，基于任务工作。

其限制是 **[smart zone（智能区）](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能清晰推理的窗口（在最新模型上约为 150k tokens）。如果会话在到达 `/to-tickets` 之前接近此限制，不要在退化状态下硬撑——在最近的阶段边界处执行 `/compact` 并继续（参见阶段边界）。

## 入口匝道

生成工作然后汇入主流程的起始情况。

- **Bug 和请求堆积** → **`/triage`**。它将 issue 推进分类角色，并生成 agent-ready 的 issue，后续由 **`/implement`** 处理。

  分类仅适用于**你没有创建的** issue——bug 报告、传入的功能请求，以及任何原始到达的问题。由 `/to-tickets` 生成的任务已经是 agent-ready 的，所以**不要对它们进行分类**。

- **有东西坏了** → **`/diagnosing-bugs`**。针对难缠的 bug：一眼看不出的 bug、间歇性故障、在两个已知正常状态之间悄悄出现的回归问题。它拒绝在没有**紧密反馈循环（tight feedback loop）**——一个能在这个 bug 上变红的命令——的情况下进行理论推测，然后用回归测试来修复。当真正的发现是没有好的接缝（seam）来锁定 bug 时，其事后分析会移交给 **`/improve-codebase-architecture`**。

- **一个庞大、模糊的任务——一个绿地项目或大型功能构建，一个会话无法完成** → **`/wayfinder`**，这是这里认知要求最高的流程。当从当前位置到目的地的路径尚不可见时，它在 issue 跟踪器上绘制一个**共享地图**的**决策任务（decision tickets）**，并逐一解决——产生**决策，而非可交付物**——直到迷雾散退、路径清晰。**`/grill-with-docs`** 打磨的是你能在一个会话中把握的想法，而 wayfinder 是为你无法把握的想法准备的——它更慢、更密集，所以请仅为此使用它，绝不要用于范围明确的功能。

  当地图清晰后，**它移交，不构建**：在 **`/to-spec`** 处汇入主流程，它将地图中链接的决策折叠成一个可构建的计划，然后按常规执行 `/to-tickets` 和 `/implement`。将地图直接循环进入 `/implement` 会跳过这个折叠，丢弃链接的细节——只有当你发现工作确实很小时，才直接进入 `/implement`。

## 代码库健康

不是功能开发——而是日常维护。

- **`/improve-codebase-architecture`** — 在有空闲时运行，保持代码库适合 agent 操作。它呈现**深化机会（deepening opportunities）**；选择一个就会_生成一个想法_，你可以将其带入主流程的 `/grill-with-docs`。它是发现候选的调查工具；**`/codebase-design`**（见下文）是你设计所选方案的工作台。

## 底层词汇

两个模型调用的参考工具，运行在*其他技能之下*——每个都是其词汇的唯一真实来源。当**词汇**（而非流程）是问题时直接使用它们；或者让上面的技能拉取它们。

- **`/domain-modeling`** — 打磨项目的*领域*语言：挑战模糊的术语，解决重载的词汇（"account" 做了三件事），将难以撤销的决策记录为 ADR。它是 `/grill-with-docs` 驱动的主动规训，保持 `CONTEXT.md` 成为一个干净的词汇表。
- **`/codebase-design`** — 深度模块词汇表（module、interface、depth、seam、adapter、leverage、locality），用于设计模块的*形状*：在一个干净的接缝（seam）上，通过小接口暴露大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用它。

## 阶段边界

一个 **phase（阶段）** 是会话中的一块工作——审查、实现、QA。在两个阶段之间的**边界**处，你有五个选项，而在整张地图中，在这五个之间做选择是最模糊的决定：

- **Continue（继续）** — 原地不动。零成本，零损失。
- **`/clear`** — 清空窗口，当这里的内容对接下来的工作无关紧要时。
- **`/handoff`** — 写一个可移植的 markdown 文件。仅限：**新工具**、**新目录**、**同事**，或在阶段中间分叉一个旁支任务。它买到的是可移植性。
- **Subagent（子 agent）** — 发送一个范围收紧的任务到它自己的窗口，拿回一份报告。
- **`/compact`** — 压缩此上下文并播种一个新会话。**默认选项**，位于树的底部，而非首选。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 获取有序决策树——五个问题、每个分支背后的推理，以及为什么主要来源（primary-source）成本使得 **Continue** 成为首先要排除的选项。在**边界处**做决定；阶段中间，继续或将其余部分拆分为子 agent。

## 独立技能

完全脱离主流程。

- **`/grill-me`** — 与 `/grill-with-docs` 相同的无情访谈，但**无状态**：它不在本地保存任何内容，也不构建 `CONTEXT.md`。当你**没有工作目录**时使用它——打磨计划、设计、文字，任何下面没有仓库的东西。如果你在工作目录中，使用 `/grill-with-docs`：它运行相同的访谈并留下文档记录，所以它严格来说是更好的那个。
- **`/grilling`** — 访谈原语本身：轮次、前沿、事实是 agent 的工作而决策是你的。`/grill-me` 和 `/grill-with-docs` 是两个命名的入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。仅当你想要没有包装的访谈时直接使用它。
- **`/resolving-merge-conflicts`** — 逐块处理进行中的合并或变基冲突，通过追溯每一侧主要来源的**意图**来解决，而非逐行挑选，然后完成操作。它永远不会运行 `--abort`。独立于所有流程之外：当你已经处于冲突中间时使用它。
- **`/prototype`** — 一个小的、一次性程序，回答一个设计问题：这个状态模型感觉对吗，或者这个 UI 应该是什么样子。一次性是对代码编写方式的约束，而非销毁的承诺：答案会折叠进真正的代码，而 prototype 本身作为**一手资料**保留在 main 的 `prototype/<name>` 分支上，从实现 issue 中指向它。它是主流程步骤 2 中的绕道，但任何难以在纸面上解决的设计问题都可以使用它。
- **`/research`** — 将阅读工作委托给一个**后台 agent**：它针对**一手资料（primary sources）**调查一个问题，然后在仓库中留下一个带引用的 Markdown 文件。它阅读时你可以继续工作。它生成的文件可以带入主流程的 `/grill-with-docs`——研究为思考提供素材，而非替代思考。
- **`/to-questionnaire`** — 当阻碍你的东西不在你脑中也不在代码库中，而在**其他人那里**时，这会给他们写一份问卷来填写。它是 `/grill-me` 的反面：不是就主题访谈你，而是就**发送**访谈你——发给谁、你需要什么回复——并将问题瞄准差距。回来的内容是 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`** — 用于只有**人类**才能执行的步骤：配置基础设施、设置凭证或 CI 密钥、点击通过不熟悉的第三方控制台、运行一次性迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL，捕获每个值，并写入 `.env` 和 GitHub 密钥——这样这个流程就不再是你每次都要向 agent 重新解释的东西。模型调用的，所以 agent 在碰到只有你能通过的障碍时会立即使用它。如果 agent 自己能做，它应该自己做；这是为真正需要人类参与的情况准备的。
- **`/wait-what`** — 对没有传达清楚的消息的纠正。在任何其他技能中间的对话中使用它，agent 会用你缺失的上下文，用 plain English，使用 `CONTEXT.md` 的词汇重新表达它刚刚说的话。它是事后补救；`/grill-with-docs` 是事前的解药，因为早期商定的共享语言才是阻止行话到来的根本。
- **`/teach`** — 跨多个会话学习一个概念，使用当前目录作为有状态的工作空间。
- **`/writing-for-agents`** — 编写 agent 消费的文档的参考：skills、AGENTS.md、定向文档。

# 分类

通过一个由分类角色组成的小型状态机来处理项目问题跟踪器上的问题。

如果此仓库将外部拉取请求视为请求表面（请参阅问题跟踪器配置），则分类也涵盖它们：**PR 是附带了代码的问题**——相同的角色、相同的状态、相同的状态机，仅增加了下面标记为"针对 PR"的少许差异。将裸的 `#42` 解析为问题或 PR，具体取决于跟踪器配置。

在分类期间发布到问题跟踪器的每条评论或问题**必须**以此免责声明开头：

```
> *本文由 AI 在分类期间生成。*
```

## 角色

两个**分类**角色：

- `bug` —— 某些功能已损坏
- `enhancement` —— 新功能或改进

五个**状态**角色：

- `needs-triage` —— 维护者需要评估
- `needs-info` —— 等待报告者提供更多信息
- `ready-for-agent` —— 完全明确，准备好由 AFK agent 处理
- `ready-for-human` —— 需要人工实现
- `wontfix` —— 不会被处理

对于 PR，相同状态对应附加的代码进行解读：`ready-for-agent` 意味着附加了简报，agent 应对 diff 采取下一步操作；`ready-for-human` 意味着准备就绪，可由人工合并。

每个经过分类的问题应携带恰好一个分类角色和一个状态角色。如果状态角色冲突，标记冲突并在执行任何其他操作前询问维护者。

这些是规范角色名称——问题跟踪器中实际使用的标签字符串可能有所不同。映射应该已经提供给你——如果没有，请运行 `/setup-matt-pocock-skills`。

状态转换：未标记的问题通常首先进入 `needs-triage`；从那里转移到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。`needs-info` 在报告者回复后返回 `needs-triage`。维护者可以随时覆盖——标记看起来异常的转换并在继续前询问。

## 调用

维护者调用 `/triage` 并用自然语言描述他们想要做什么。根据请求进行解释并执行。示例：

- "显示任何需要我关注的内容"
- "让我们看看 #42"（问题或 PR）
- "将 #42 移到 ready-for-agent"
- "哪些已经准备好让 agent 处理了？"

## 显示需要关注的内容

查询问题跟踪器并呈现三个分组，按最旧的优先：

1. **未标记** —— 从未分类过。
2. **`needs-triage`** —— 评估进行中。
3. **`needs-info` 且有报告者自上次分类笔记以来的活动** —— 需要重新评估。

当 PR 在范围内时，将外部 PR 包含在这些分组中，并标记每一行为 `[PR]` 或 `[issue]`。发现只显示*外部* PR（跟踪器配置定义了谁算外部）——协作者进行中的 PR 不属于分类工作。此筛选仅用于发现；明确命名的 PR 无论作者如何始终进行分类。

显示计数和每个项目的单行摘要。让维护者选择。

## 分类特定问题或 PR

1. **收集上下文。** 阅读完整的问题或 PR（正文、评论、标签、作者、日期；对于 PR，还要阅读 diff）。解析任何先前的分类笔记，以免重新询问已解决的问题。使用项目的领域词汇探索代码库，尊重相关区域的 ADR。对代码库进行两项检查：(a) **冗余**——按领域概念（而不仅仅是请求的措辞）搜索请求行为的现有实现，并报告查找位置。如果找到，则属于已实现的 `wontfix`（步骤 5）。(b) **先前拒绝**——阅读 `.out-of-scope/*.md`，找出任何与本请求相似的内容。

2. **给出建议。** 告诉维护者你的分类和状态建议以及理由，加上与请求相关的简要代码库总结——包括是否已实现。等待指示。

3. **验证主张。** 在任何追问之前，检查主张是否成立。对于 bug，按照报告者的步骤复现。对于 PR，确认 diff 是否如其所说——检出代码，运行相关测试或命令。报告结果：已确认（附带代码路径）、失败或细节不足（这是一个强烈的 `needs-info` 信号）。已确认的验证会产生更强的 agent 简报。

4. **追问（如果需要）。** 如果请求需要充实细化，一起运行 `/grilling` 和 `/domain-modeling` 技能——一轮一轮问题地进行追问，锐化领域术语，并在决策确定时内联更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent` —— 发布一条 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` —— 结构与 agent 简报相同，但注明为何无法委派（判断调用、外部访问、设计决策、手动测试）。
   - `needs-info` —— 发布分类笔记（模板如下）。
   - `wontfix` —— 关闭，评论取决于*原因*：
     - **已实现** —— 变更已存在于代码库中。指出其位置；**不要**写入 `.out-of-scope/`（该知识库用于*被拒绝的*请求，而非已构建的）。
     - **已拒绝（bug）** —— 礼貌解释，然后关闭。
     - **已拒绝（增强）** —— 写入 `.out-of-scope/`，从评论中链接它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` —— 应用角色。如有部分进展可添加可选评论。

## 快速状态覆盖

如果维护者说"将 #42 移到 ready-for-agent"，信任他们并直接应用角色。确认你将执行的操作（角色变更、评论、关闭），然后执行。跳过追问。如果在没有追问会话的情况下移动到 `ready-for-agent`，询问他们是否要编写 agent 简报。

## Needs-info 模板

```markdown
## 分类笔记

**我们目前已确定的内容：**

- 要点 1
- 要点 2

**我们仍需要你（@reporter）提供的内容：**

- 问题 1
- 问题 2
```

在"已确定的内容"下捕获追问期间解决的所有内容，以免工作丢失。问题必须具体且可操作，不能是"请提供更多信息"。

## 恢复之前的会话

如果问题或 PR 上存在先前的分类笔记，阅读它们，检查报告者是否回答了任何未解决的问题，并在继续前呈现更新的情况。不要重新询问已解决的问题。

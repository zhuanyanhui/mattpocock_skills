---

当用户想要创建重构请求时调用此 skill。你应该按照以下步骤进行。如果你认为某些步骤不必要，可以跳过。

1. 请用户提供他们要解决的问题的长篇详细描述，以及任何可能的解决方案想法。

2. 探索仓库以验证他们的说法并理解代码库的当前状态。

3. 询问他们是否考虑过其他方案，并向他们展示其他选项。

4. 与用户详细讨论实现方案。要极其详细和彻底。

5. 敲定实现的确切范围。确定你计划更改的内容和计划保持不变的内容。

6. 在代码库中检查该区域的测试覆盖情况。如果测试覆盖不足，询问用户的测试计划。

7. 将实现分解为极小的提交计划。记住 Martin Fowler 的建议："让每个重构步骤尽可能小，这样你总能看到程序正常运行。"

8. 使用以下模板创建包含重构计划的 GitHub issue：

<refactor-plan-template>

## 问题陈述

从开发者视角描述开发者面临的问题。

## 解决方案

从开发者视角描述问题的解决方案。

## 提交计划

一份长而详细的实现计划。用通俗语言编写计划，将实现分解为尽可能小的提交。每次提交都应使代码库处于可工作状态。

## 决策文档

已做出的实现决策列表。可以包括：

- 将要构建/修改的模块
- 将要修改的那些模块的接口
- 来自开发者的技术澄清
- 架构决策
- 模式变更
- API 契约
- 特定交互

**不要**包含特定的文件路径或代码片段。它们可能很快就会过时。

## 测试决策

已做出的测试决策列表。包括：

- 什么构成好测试的描述（仅测试外部行为，不测实现细节）
- 哪些模块将被测试
- 测试的先例（即代码库中类似类型的测试）

## 超范围

本次重构范围之外的描述。

## 补充说明（可选）

关于重构的任何其他说明。

</refactor-plan-template>

## 作用

`prototype` 编写**用于回答问题的一次性代码**——这个状态模型感觉对吗，或者这个页面应该长什么样。问题优先，它决定后续一切内容的形态；回答错误问题的原型无论多好看都是纯粹的浪费。

"一次性"是对代码*编写方式*的约束，而不是承诺要销毁它。没有测试，除了让代码能跑之外没有错误处理，没有抽象，没有持久化——因为这些都无助于你学到你想学的那一件事。最终留存下来的是答案，融入真实代码中，而原型本身则停放在 main 之外的一个分支上，作为答案来源的证据。

## 何时使用

输入 `/prototype`，或者当任务匹配时 [agent](https://www.aihero.dev/ai-coding-dictionary/agent) 会自动调用它。

在你遇到无法通过讨论解决的问题的那一刻就使用它——一个你无法在脑海中穷尽边界情况的状态机，一个不看三个并排版本就无法想象的页面。[grilling](https://www.aihero.dev/ai-coding-dictionary/grilling) 会话正是在这类问题上膨胀失控的：agent 换着方式重述，你猜测着回答，范围随着不确定性不断扩大。停下来，构建一次性版本，看着它，然后用一句话回答。如果是已经构建好的东西行为异常，你想知道为什么，那就用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)——原型探索的是"该构建什么"，而不是"为什么已构建的东西坏了"。

你也会在没有主动选择的情况下到达这里。[wayfinder](https://aihero.dev/skills-wayfinder) 会在其地图上创建 `prototype` 决策任务，完成一个就是使用这个技能。

## 两个分支

问题决定分支，而分支产出的工件截然不同：

- **"这个逻辑/状态模型感觉对吗？"**——一个**单一的可共享 HTML 文件**。一个自包含的页面，无需构建、无需服务器，双击即可打开。它带有一个带标签的状态面板，每次点击后重新渲染；用于按任意顺序试探模型的自由操作按钮；以及带标签页的**引导式 walkthrough**——每个标签页一个场景，下方排列着需要按顺序点击的按钮。所有内容都使用领域语言标注，因此你可以把它交给设计师、产品经理或领域专家，让他们自己感受这个模型。页面背后的逻辑是一个小型纯模块——一个 reducer、一个状态机、一组函数——与 DOM 保持干净隔离，因此验证后的版本可以直接提升到真实代码中。
- **"这个页面应该长什么样？"**——在同一路由上呈现几种**截然不同的** UI 变体，通过底部浮动栏和 `?variant=` URL 参数切换。变体必须在结构上有分歧，而不是颜色；三个微调过的卡片网格只是墙纸，不是原型。只要可能，它们就应该在真实页面中渲染，使用真实数据和真实密度，因为在真空中评判的变体看起来总是没问题。

两者都将状态保留在内存中，开始时无需思考，并在每一步之后向你展示完整状态。当你发现自己开始硬化某个原型——添加测试、连接真实数据库、为将来可能需要的情况做通用化——你就已经不再是原型了。

## 原型是一手资料

完成的原型会留下两样东西，它们去往不同的地方。

**答案**——结论加上它所解决的问题——被持久地记录下来：一条 commit 消息、一条 ADR、一个实现任务。这是 main 分支保留的东西，融入真实代码中。

**原型**是可运行的答案来源证据，不会被删除。它也不属于 main——那里没有什么值得维护的，而且它很快就会过时——因此它被提交到一个一次性 `prototype/<name>` 分支上，该分支从 main 分出，永远不会合并，并在实现任务上留下指向该分支的[上下文指针](https://www.aihero.dev/ai-coding-dictionary/context-pointer)。main 保持干净；探索过程保持可查找、可重新运行，供下一个接手这项工作的人使用。

## 常见问题

**等等——原型不是应该被删除吗？**
现在不了。以前是：构建它，保留答案，扔掉代码。最尖锐的反对意见从来不是关于速度——而是*下一个会话谁来接手这项工作，他们有什么可以依赖的？*对原型的文本摘要会丢失让它具有说服力的东西。因此现在原型被当作[一手资料](https://www.aihero.dev/ai-coding-dictionary/primary-source)来对待：它落在 main 之外的一个 `prototype/<name>` 分支上，实现任务指向它。改变的是代码存放的位置，而不是纪律——它仍然永远不会合并到 main 中。

**以前它构建的是终端应用。那个去哪了？**
逻辑分支现在改为输出一个可共享的单一 HTML 文件。终端应用只能由已克隆仓库并安装了运行时的人来驱动，而这恰恰排除了原型最需要其意见的人——设计师、产品经理、知道状态模型应该意味着什么的领域专家。一个双击即可打开、通过邮件发送也能使用的自包含文件，任何人都能驱动。其下方的纯逻辑模块没有改变，仍然是提升到真实代码中的部分。

**一个 agent 告诉我去 `/prototype`，但我应该在做实现。**
这是一个已知问题，也是命名问题。`prototype` 是一个通用、吸引人的词，对不了解工作流的 agent 来说，一旦任务存在就会被解读为"显而易见的下一步"，所以即使设计已经在讨论中完全确定，它也会被按名字推荐。如果你已经知道要构建什么，下一步就是按任务执行 `/implement`。只有在某个具体设计问题确实未解决、讨论也无法解决时，才使用原型。

**我应该在构建任何生产功能之前先原型化整个应用程序吗——比如用来向潜在客户演示？**
那是另一个挂着这个技能名字的工件。这里原型的作用域限定为一个问题，而"整个应用是什么"不是一个可以回答的问题。全应用原型没有自然的停止点，因此它会靠动量变成生产应用：清理永远不会发生，而在原型规则下编写的代码——没有测试、没有错误处理——最终会出现在用户面前。如果你需要销售演示，就刻意把它作为 demo 来构建，并明确说明其中没有任何生产代码。如果你需要解决一个设计问题，就把它缩减到那个问题。

**如何在它自己的会话中运行？**
原型位于自己的目录中，会产生大量[上下文](https://www.aihero.dev/ai-coding-dictionary/context)，你不希望这些上下文出现在提出问题的那个线程中，所以在别处运行，只带回答案。[handoff](https://aihero.dev/skills-handoff) 是双向的桥梁。

**这不是烧掉 token 最快的方式吗？**
如果你原型化了本来可以通过讨论回答的问题，或者让一个原型蔓延到整个功能，确实可能是。重要的比较不是 token 与零的对比，而是 [token](https://www.aihero.dev/ai-coding-dictionary/token) 与构建了错误的状态模型、在生产调用者接入后才发现的对比。保持问题聚焦、运行简短，花费就会保持合理。

## 判断标准

- 你能用一句话说出原型存在的目的是回答什么问题——而且它写在 demo 的顶部，不只是在你脑海里。
- 不读代码的人也能驱动逻辑 demo。他们打开文件，在 walkthrough 标签页中按下按钮，然后用自己的话描述看到的内容。
- 有人说"等等，这不应该可能发生"或者"啊，我以为 X 是这样的"。这就是*想法*中的 bug，而这正是全部意义所在。
- UI 变体在布局和信息层次结构上有分歧，而不仅仅是颜色和文案——你得到的反馈是"B 的头部配上 C 的侧边栏"。
- 一次会话内就能回答。如果过了一天还在构建，说明问题太大了；拆分它。
- 结束后，main 包含决策而不包含原型中的任何内容，实现任务指向仍然持有原型的那个分支。

## 定位

`prototype` 是一个**随时可调用的独立技能**——你进入它来解决一个设计问题，然后退出——它同时也是其他技能运行的机制。

它最大的消费者是 [wayfinder](https://aihero.dev/skills-wayfinder)。wayfinder 地图由**决策任务**组成，而 `prototype` 是任务可以是四种类型之一：当阻塞性问题是"应该长什么样"或"应该如何行为"、无论多少讨论都无法解决时使用的那种。wayfinder 通过构建具体的东西来回应，提升了模糊讨论的保真度，而这个技能就是构建那个具体东西的方式。原型任务通过答案来解决，原型作为资源链接在地图上。

其他上下游邻居也是如此。[grill-me](https://aihero.dev/skills-grill-me) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 回答可以被 grill 的问题；无法被 grill 的问题来到这里，而一句话答案会回到访谈中。下游，经过验证的状态模型或 UI 方向成为 [to-spec](https://aihero.dev/skills-to-spec) 的已确定输入，它可以内联原型产出的包含关键决策的片段，而不是用文本描述它。对于其他一切，[ask-matt](https://aihero.dev/skills-ask-matt) 会将你路由到整个集合。

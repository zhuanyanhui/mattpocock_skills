## 它做什么

`improve-codebase-architecture` 会调查代码库中的**深化机会**——即那些浅度模块（接口几乎与它隐藏的内容一样复杂）可能变为深度模块的地方——将它们写成一份自包含的 HTML 报告，然后对你挑选的任意候选进行[无情访谈](https://www.aihero.dev/ai-coding-dictionary/grilling)。

它从不改动代码。整个运行过程只会在你的操作系统临时目录中生成一个 HTML 文件和一场对话；重构本身稍后在独立的[会话](https://www.aihero.dev/ai-coding-dictionary/session)中通过正常的构建流程进行。这正是它是一项调查而非重构工具的原因，也是它值得在你还没准备好动手的代码库上运行的原因。

两个过滤器防止报告变成通用的清理建议。每个候选都必须通过**删除测试**——移除这个模块会让复杂性集中在更小的接口后面，还是只是分散到调用方？只有"集中"的情况才能赢得一张卡片。除非你把它指向特定区域，否则它会先读取最近的 commit 历史，并将扫描偏向那些正在积极变更的路径，理由是没人碰的代码中的深化是一次你永远无法兑现的重构。

## 何时使用它

你通过输入 `/improve-codebase-architecture` 来调用它——[agent](https://www.aihero.dev/ai-coding-dictionary/agent) 不会自行调用它。

它位于构建循环之外——它不是主循环中的一个步骤，而是你定期运行以排队更多改进代码库工作的东西。它被使用的四种情况：

| 情况 | 如何使用 |
| --- | --- |
| 例行维护 | 每隔几天运行一次，或在有空闲时运行，以防止功能之间的结构腐化。 |
| 大型构建之前 | 把它指向[规范](https://www.aihero.dev/ai-coding-dictionary/spec)："我们如何让这次变更变得容易？"这是它最有效的提示。 |
| 非全新项目审计 | 在大型、无结构或[vibe-coded](https://www.aihero.dev/ai-coding-dictionary/vibe-coding)的仓库上运行它，以了解它的实际状况。 |
| 遗留测试工作 | 用它先找到缺失的接缝，然后再对不可测试的代码编写测试。 |

与相邻技能容易混淆的地方：

- 对于设计你已经选定的一个模块，使用[codebase-design](https://aihero.dev/skills-codebase-design)——那是工作台，这是找到该放什么到工作台上的调查。
- 对于大到无法在一次会话中把握的整个工作，使用[wayfinder](https://aihero.dev/skills-wayfinder)。
- 对于"这个具体的东西坏了"，使用[diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)。当真正的发现是没有好的接缝来锁定 bug 时，它会交回这里。

## 前置要求

运行它没有前置要求。如果存在的话，它会读取 `CONTEXT.md` 和 `docs/adr/` 中的任何 ADR，并在你的领域的名词存在时用它们自己的名词说话——一个候选读起来是"深化订单接收模块"，而不是"重构 FooBarHandler"。

它在两个地方写入。报告放到 `<tmpdir>/architecture-review-<timestamp>.html`，在仓库之外。在无情访谈循环期间，它会在 `CONTEXT.md` 中添加或完善术语，如果该文件不存在则创建它，并提供将拒绝的候选记录为 ADR，这样未来的运行不会再次建议它。

## 深度，以及寻找它的报告

这个技能基于一个核心想法：**深度**。深度模块将大量行为放在一个小而稳定的接口后面。浅度模块则通过一个与其底层代码几乎一样宽的接口泄漏其实现。报告就是对浅度性的猎杀——仅为可测试性而提取的纯函数，而真正的 bug 存在于它们被调用的方式中（没有**局部性**），跨越**接缝**泄漏的模块，不打开五个文件就无法理解的概念——以及修复它的深化提案。

每个候选都是一张卡片：涉及的文件、摩擦、用通俗英语表述的解决方案、以**局部性**和**杠杆效应**表述的收益、前/后对比图，以及一个强度徽章。

| 徽章 | 对你的含义 |
| --- | --- |
| `Strong` | 删除测试明确通过且摩擦真实存在。认真对待这些。 |
| `Worth exploring` | 合理的深化，但收益取决于代码下一步的走向。 |
| `Speculative` | 为完整性而提出。其中大多数可以安全忽略。 |

报告以一个**顶级推荐**结尾——它首先会处理的那个——然后技能停止并询问你想探索哪个候选。此时还没有做任何决定，也没有移动任何代码。

## 挑选一个之后会发生什么

挑选一个候选会启动关于它的[无情访谈](https://aihero.dev/skills-grilling)会话：约束、接缝后面有什么、哪些测试保留、深化后的接口应该长什么样。该会话的输出是一个决策，而不是 diff。之后应用正常流程——将决策带入[to-spec](https://aihero.dev/skills-to-spec)，然后是[to-tickets](https://aihero.dev/skills-to-tickets)，然后是[implement](https://aihero.dev/skills-implement)。

## 常见问题

**它围绕一个想法无情地追问了我一个小时，而不是给我展示选项。我能关掉这个吗？**

可以——在调用它时说出来（"不要对我无情访谈，只展示报告"）。这是该技能被抱怨最多的地方。一个用户直言不讳：他们喜欢它作为"获取全面改进分析的便捷方式"，但在添加无情访谈循环后发现它"几乎无法使用"，报告了它提出一个解决方案然后问"几十个甚至上百个问题"的会话。设计意图是报告先来，访谈只在你选择的候选上开始，但较弱的[模型](https://www.aihero.dev/ai-coding-dictionary/model)会跳过报告直接开始就它们的第一个想法对你进行访谈。该线程中的报告因模型而异，这是一个开放问题——该技能还没有文档化的拒绝访谈模式。

**报告打开为无样式的原始 HTML 且没有图表。发生了什么？**

报告从 CDN 加载 Tailwind 和 Mermaid，所以打开它时需要网络访问，当某些东西阻塞这些脚本时它会静默崩溃。归档的案例是一个安全钩子要求 SRI 哈希：agent 添加了它们，CDN 提供给浏览器的字节与用于计算哈希的 `curl` 不同，浏览器阻塞了脚本。离线和锁定环境也会碰到同样的墙。agent 看不到这个，因为它从不渲染页面。变通方法是要求内联 CSS 和手工构建的 SVG 图表来代替 CDN 脚手架。这是一个开放问题，也是一个真正的粗糙边缘。

**它给了我十二个候选。我在同一个会话中处理它们还是开始新的会话？**

每个会话一个候选。在一次对话中处理多个候选会用报告、无情访谈、领域模型编辑和代码变更同时填满[上下文窗口](https://www.aihero.dev/ai-coding-dictionary/context-window)。报告只存在于临时文件中，所以携带候选本身而不是文件：挑选一个，进行无情访谈，将决策带入 `/to-spec`，然后将其余的变成[tickets](https://www.aihero.dev/ai-coding-dictionary/ticket)，你可以稍后独立领取。将选定的改进放入规范中，而不是直接进入实现。这是一个反复出现的问题，在技能本身中没有文档化的工作流。

**我应该如何提示它？**

带着你下一个正在构建的东西来提示。当大型构建即将到来时，把它指向规范并问"我们如何让这次变更变得容易？"无提示的运行会自行扫描热点，这对于例行维护没问题，但指明方向才能让报告变得可操作。

**它在大型遗留代码库上能用吗？**

部分能用。它在缺少一致结构的大型现有代码库上表现出色，也是一次性结构设置之后推荐的维护机制。诚实的反对面：拥有真正失控项目的用户报告它"有一点帮助但仍然不够用"，一位拥有八年遗留代码库的开发者报告模型在兜圈子，同样的技能在整洁的仓库上能生成清晰的图表。那个案例还没有专用的 `/refactor` skill。如果代码库根本没有共享词汇，先用[grill-with-docs](https://aihero.dev/skills-grill-with-docs)来建立一个词汇表往往能让这个技能的输出好得多。

**它和 `/codebase-design` 有什么不同？**

`/codebase-design` 是一个参考，而不是会话驱动器。它提供词汇——模块、接口、深度、接缝、适配器、杠杆效应、局部性——这个技能借用了它。把一个新 agent 指向 `/codebase-design` 让它去"做"是一个已知的失败模式：没有自己的流程可遵循，agent 会发明一个，重新探索代码并运行很长时间才问你任何问题。用这个技能驱动；消费那个技能。

**它会告诉我代码库没问题吗？**

很少会，你应该事先知道这一点。这个技能被构建为输出发现，所以它的框架推动它生成候选，而不是得出结论说一切正常。强度徽章是防御——一份所有内容都是 `Speculative` 的报告就是技能在告诉你它什么也没发现，这是它唯一知道的方式。

**它在 Codex 或其他 harness 中能用吗？**

部分能用。探索步骤直接命名了 Claude Code 的 `Agent` 工具配合 `subagent_type=Explore`，所以一个没有该工具的[harness](https://www.aihero.dev/ai-coding-dictionary/harness)可能会跳过并行探索而不是替换它自己的工具。技能仍然能运行；只是扫描不那么彻底。一个 harness 中立的改写已被提出但尚未合并。

**我该如何在 TypeScript 中实际实现深度模块？**

技能没有附带好的答案。反复出现的请求是一个给出原则的具体文件和模块布局的 `TYPESCRIPT.md`，但它不存在。技能会告诉你深化应该在哪里以及接缝后面应该有什么；将其翻译为包或目录结构目前取决于你自己。

## 它在正常工作的标志

- 候选使用你的领域的概念命名，而不是发明的类名——"订单接收模块"，而不是"FooBarHandler"。
- 候选聚集在你最近编辑过的文件中，而不是仓库的休眠角落。
- 运行期间没有代码被改动。唯一的新文件是临时目录中的 HTML 报告。
- 它在报告之后停下来询问你想要哪个候选，而不是自行继续。
- 每张卡片都以局部性或杠杆效应解释收益，并说明哪些测试会变得更简单——而不只是"这样更整洁"。
- 因持久原因拒绝候选会让你得到记录 ADR 的提议，这样下次运行不会再次建议它。

## 它的定位

`improve-codebase-architecture` 是**定期维护**——每隔几天运行一次，在任何链之外，以排队工作而不是执行工作。它的邻居是[codebase-design](https://aihero.dev/skills-codebase-design)，拥有每个候选所使用的深度和接缝词汇；[grilling](https://aihero.dev/skills-grilling)，在你选定候选后遍历决策树；[domain-modeling](https://aihero.dev/skills-domain-modeling)，在决策落定时保持 `CONTEXT.md` 和 ADR 的更新。它产生的是一个想法，该想法通过[grill-with-docs](https://aihero.dev/skills-grill-with-docs)或[to-spec](https://aihero.dev/skills-to-spec)重新进入主构建流程。至于哪个技能适合哪种情况，[ask-matt](https://aihero.dev/skills-ask-matt)是整个集合的路由器。

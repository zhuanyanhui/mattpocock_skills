## 它做什么

`handoff` 将当前对话压缩成一份**交接文档**——一个 markdown 文件，写入你操作系统的临时目录而非工作区中，供全新的 [agent](https://www.aihero.dev/ai-coding-dictionary/agent) 读取并接手工作。

它带来的是**可移植性**，而非压缩。这让该技能比听起来更窄。你只有在工作必须*转移*时才需要这个文件——换到一个新的 [harness](https://www.aihero.dev/ai-coding-dictionary/harness)、新目录、同事手里，或者你想派生出去的副任务。如果没有东西需要转移，你不需要交接：留在当前 [会话](https://www.aihero.dev/ai-coding-dictionary/session) 中、`/clear`、[subagent](https://www.aihero.dev/ai-coding-dictionary/subagent) 和 `/compact` 就能覆盖普通的阶段结束场景，而且 `/compact` 比这个技能更常用。

## 何时使用

通过输入 `/handoff` 调用——agent 不会自己调用它。传递一条关于下次会话用途的备注，文档就会据此编写。

以下四种情况就是完整的触发条件：

| 情况 | 为什么需要文件 |
| --- | --- |
| 更换 harness —— Claude → Codex | 新 harness 无法看到旧的 [上下文](https://www.aihero.dev/ai-coding-dictionary/context) |
| 迁移到不同目录或仓库 | 原型目录是常见场景 |
| 将工作发给同事 | 他们需要一个可读的东西 |
| 阶段中发现的副任务需要派生 | 你继续工作；第二个 agent 接手派生任务 |

其他任何情况——同一个 harness、同一个目录、你已完成 [grilling](https://www.aihero.dev/ai-coding-dictionary/grilling) 并要进入实现——`/compact` 才是正确的选择。[ask-matt](https://aihero.dev/skills-ask-matt) 在阶段边界处涵盖了全部五个选项的有序决策树。

## 分支是人们跳过的用法

该技能的描述读起来像是会话恢复：写个总结，在此结束，在那里恢复。这样理解的话，它看起来就像一个更差的 `/compact`，所以人们就略过去了。派生场景才是真正值得知道的。你**留在自己的会话中**，把积累的上下文副本交给第二个并行工作的 agent。

这正是绕道 [prototype](https://aihero.dev/skills-prototype) 时的用法。你正深入一个设计对话，遇到了一个只有运行代码才能解决的问题，你不想把已经建立的讨论线索浪费在寻找答案上。交接给一个原型会话，拿到答案，交回给原线程，并在原始线程中引用它。两次跨越，一个活跃对话，无需重新解释任何东西。

阶段边界处的五个选项中，有三个保留了不同的东西：`/compact` 保留你的意图，`/clear` 什么都不保留，`/handoff` 保留工作转移的能力。

## 什么跟着走，什么不跟着

文档携带活跃的线程——进行中的工作、为什么、下一步是什么——以及一个**建议技能**部分，指明下一个 agent 应该调用什么。写入之前会遮蔽所有机密信息。

它刻意不携带的是已经写在别处的东西。规格、计划、ADR、issues、commits 和 diffs 通过路径或 URL 引用，从不复制。这让文件保持小巧，也让已确定的细节集中在一个地方，而不是两处各自漂移。

## 常见问题

**Handoff 还是 compact？**
除非有东西需要转移，否则用 `/compact`。停留在同一个任务是 compact 而非 handoff——同一个 harness、同一个目录、你需要留在循环中，这是阶段边界决策树大多数时候的落脚点。`/handoff` 的优势不在于它总结得更好；而在于它的结果是一个文件，你可以带到 `/compact` 无法到达的地方。

**那么 compact、clear 和 handoff 的实际区别是什么？**
三样不同的东西被保留。`/compact` 压缩当前上下文并让你在新窗口中继续——意图得以保留。`/clear` 清空窗口从零开始——当你身后的一切都可丢弃时才正确，如果不是则是一条单行道。`/handoff` 写一个可移植的文件——工作能在转移到别处后存活。注意这三者都将**[一手资料](https://www.aihero.dev/ai-coding-dictionary/primary-source)**（对话的实际发生）转化为**[二手资料](https://www.aihero.dev/ai-coding-dictionary/secondary-source)**（对它的总结）。继续是唯一不会这样做的方法，这也是为什么它是首先要排除的选项。

**我的手稿文件去哪了？**
临时目录，这是该技能最常见的摩擦点：路径很长、每个操作系统不同，而且在 Windows 上 agent 有时需要好几次才能找到正确的位置。在继续之前，要回路径并保存好。使用临时目录是刻意的：交接是一份转移文档，不是你要维护的制品。它也不是一个持久化的东西——见下一个问题。

**我的交接文件在会话之间消失了。**
有些环境会在会话之间清除临时目录——Codex 是已报告的案例——而 `/private/tmp` 在重启时消失。如果下次会话不是在一小时内开始，或者在另一个 harness 下开始，在文件写入后尽快自行将其复制到持久的位置。文档*指向的*任何东西也适用同样的规则：一个引用了临时目录中其他文件的交接，是下一个 agent 无法跟进的交接。

**我实际怎么把它交给下一个 agent？**
打开新会话并指向那个路径：读取这个文件，然后继续。指向文件而不是把总结粘贴到 shell 命令中——包含反引号或 `$(...)` 的总结在 `claude "<summary>"` 中插值时会被弄乱，而通常的失败是静默截断而非报错，所以新 agent 会在一个悄然不完整的简介下开始工作。

**这和 `/branch`、`--fork-session` 或内置的 `/handoff` 一样吗？**
类似，但不完全相同，而且 `/branch` 并不是这里发布的技能——`/handoff` 才是规范名称。fork 继承上下文的精确副本；这个技能产生的是一个*针对性的*压缩，面向一个已声明的下一个任务，以文件形式呈现。当 fork 能胜任时——同一台机器、同一个 harness、同一个目录——fork 的工作量更少。一旦目标所在是 fork 无法到达的地方，文件方案就胜出。

**什么时候内容应该放在 `CLAUDE.md` 而不是交接文件里？**
问自己：下个月还成立吗？`CLAUDE.md` 是关于项目的常驻上下文，无论是否相关都会加载到每个会话中。交接针对的是一项进行中的具体工作，在该工作落地后就失效了。反复被重新解释的事实是 `CLAUDE.md` 要解决的问题；一个半完成的任务是交接要解决的问题。

**它捕获了 what，却没捕获 why。**
这是一个公正且反复出现的批评。有两件事有帮助。传递参数——告诉它下次会话要做什么——这样与*那个*相关的推理会被保留而不是被压平。同时留意那些会话从未真正验证过的自信断言："X 没有构建"、"Y 已完成"。下一个 agent 会把文档当作契约，不会重新检查它，所以写成事实的信念会变成后续一切的错误前提。在交接之前阅读文档，把你只是假设的内容降级处理。

**为什么它是一个技能而不是斜杠命令？**
两者都行；它们适合不同的场景。作为技能，它通过与其他东西相同的安装路径来发布和更新，这正是它可共享的原因——agent 不会自己触发它的约束是由其 frontmatter 设定的，而非由机制设定。

## 它生效的标志

- 文档只占对话的一小部分，规格、issues 和 diffs 以路径和 URL 的形式出现，而不是复制的文本。
- 你可以在没有打开原始会话的情况下冷读它，并且知道下一步该做什么。
- 新 agent 开始工作，而不是要求你重新解释设置。
- 在派生场景中，当你回来时你的原始会话仍然原封不动地坐在那里。
- 建议技能部分列出了你自己也会想到的技能。
- 里面没有任何密钥、token 或密码。

## 在体系中的位置

`handoff` 是一个**随时可调用的独立技能**，位于会话之间的接缝处，而不是构建链内部——但它的接缝很窄，诚实的图景是你使用它的频率会低于阶段边界处其他四个选项。它最近的邻居是 [prototype](https://aihero.dev/skills-prototype)，因为原型有自己的目录，来回的往返正是这个技能所针对的跨越。当你在边界处不确定是否应该继续、清除、交接、委托还是压缩时，[ask-matt](https://aihero.dev/skills-ask-matt) 携带了排序这五个选项的决策树——并将你路由到其余技能。

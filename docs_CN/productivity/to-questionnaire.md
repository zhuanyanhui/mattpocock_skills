## 功能说明

`to-questionnaire` 将你自己无法做出的决策转化为一**问卷**——一份 Markdown 文档，交给那个掌握你所缺失信息的人，供他们异步填写，或者在会议中共同完成。

它只**审视**你关于**发送**的情况，而不会审视主题本身。在这里追问主题是没有意义的：正是因为不了解主题，你才需要写信给别人。所以它只问两个你总能回答的问题——这份问卷要发给谁，以及你需要对方反馈什么——并将文档中的每个问题都对准两者之间的**缺口**。

## 何时使用

你通过输入 `/to-questionnaire` 来调用它——[agent](https://www.aihero.dev/ai-coding-dictionary/agent) 不会主动调用它。

当某个决策被阻塞在另一个人头脑中的知识上时使用它：客户、领域专家、掌握业务规则的高管、不在同一个团队的同事。选择哪个 skill 取决于答案实际上在哪里：

| 答案在…… | 使用 |
| --- | --- |
| 你自己的头脑中，但还没有理顺 | [grill-me](https://aihero.dev/skills-grill-me) |
| 代码库中 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 别人的头脑中 | `to-questionnaire` |
| 还没有人的头脑中——需要先有东西来引发反应 | [prototype](https://aihero.dev/skills-prototype) |

常见情况是 [grilling](https://www.aihero.dev/ai-coding-dictionary/grilling) 会话陷入停滞：浮现出的某些问题不是你能回答的。在同一个对话中运行 `/to-questionnaire` 将这些问题转到线下，然后带回答案继续推进。

## 关注发送，而非主题

访谈只有两轮交换，然后就停止。

- **要发给谁？** 对方的角色、专长、与你的关系。这决定了文档的语气以及需要承载多少上下文信息——外部客户需要让理解背景，队友则不需要。
- **你需要什么反馈？** 你无法独自解决的具体决策或事实。这会成为衡量最终文档的清单：你列出的每个条目都会对应一个针对它的问题。

之后的内容就是起草。文件会以 `to-questionnaire-<slug>.md` 的名称保存到当前目录下。无需设置、无需工作区、无需配置。

## 文档结构

它被框定为一份**探索性问卷**——你缺少上下文，接收者掌握信息——这种框定决定了它的形态：

- 一行目的说明，指出依赖这份问卷的决策，以及一段简短的背景部分，面向从未了解过你想法的接收者。
- 问题按**最重要优先**排序，并按主题分组，因为异步意味着你可能只有一次机会。
- 每个问题只包含一个想法，绝不复合，下方留有回答空白，并且仅在问题可能被误解时才附带*为什么问这个*的说明。
- 明确允许回答"我不知道"——标记出的不确定性是有用的；而读起来像事实的自信猜测则不是。
- 一个结尾的兜底问题：有什么我们没有问到但你应该告诉我们的吗？

有两点它刻意不做。它不**分支**——问题是一个扁平的分组列表，而不是一棵树（如果你回答了 A 就跳过 D 部分）。它也不**多接收者**——一次运行生成一份文档，对应一个人。

## 常见问题

**它会读取我的 grilling 会话并从中提取问题吗？**

不会作为一个独立的步骤。这个 skill 没有摄入阶段：它询问发送情况，然后起草。为什么在 grilling 会话之后它能正常工作，是因为你在**同一个会话**中运行它，所以 [session](https://www.aihero.dev/ai-coding-dictionary/session) 已经在 [context](https://www.aihero.dev/ai-coding-dictionary/context) 中，起草可以利用这些内容。在全新的会话中启动它，它对之前的 grilling 一无所知——当你回答"你需要什么反馈"时，你需要自己重新提供主题。

**缺失的答案不在同一个人那里。它能按接收者拆分吗？**

不能。第一步询问的是接收者，单数，整个文档的语气和上下文都是针对他们的。如果三个人分别掌握答案的三个部分，就运行三次，每人一次。有人在一份文档内按学科或角色路由问题的需求我们收到过；但这不是已发布的版本。

**问题是依赖性的吗——它会根据之前的答案跳过某些部分吗？**

不会。依赖性问题设计曾经过探索但没有发布。输出是一个静态文档：主题分组、最重要优先、每个问题都是活的。反对意见是合理的——一个 [model](https://www.aihero.dev/ai-coding-dictionary/model) 在得到真实答案之前计划超过两三个问题就会计划不当，而一个分支文档必须在每个答案之前计划所有问题。

**如果接收者也不知道呢？**

文档会告诉他们这样说。明确要求回答"我不知道"和部分答案，因为标记出的不确定性比猜测更有价值——含糊的答案和自信的错误答案一旦回到你的上下文中看起来是一样的。

**它会发送到哪里吗——Slack、issue 跟踪器、邮件？**

不会。它在当前目录下写入一个 Markdown 文件并告诉你路径。交付由你自己决定：粘贴到 [ticket](https://www.aihero.dev/ai-coding-dictionary/ticket) 中、丢到 Slack 线程里、附加到邮件上，或者在共享屏幕上打开并实时过一遍。这四种方式都有人手动对接过。

**这不就是批处理模式的 `/grill-me` 吗？**

不是，而且这个区分值得把握。`grill-me` 已经按**轮次**提问——一次性问完整个前沿，然后根据你的答案重新计算——所以"一次性给我所有问题"的需求已经在那里满足了。`to-questionnaire` 关注的是不同的轴：不是问题如何传递，而是答案在谁的头脑中。更快地自己回答这些问题用 `grill-me`；从别人那里获取答案用这个。

**没有 skill 我能不能直接让 agent 帮我做？**

可以，而且在它存在之前很多人就是这么做的——`OPEN_QUESTIONS.md` 文件、发给客户的电子表格、每个未回答问题一个"需要更多信息"的工单。这个 skill 带给你两样东西：访谈永远不会偏离到主题本身，而且文档会生成一个非技术接收者真正能填写的格式。如果你已经有了一个行之有效的内部格式，诚实的回答是你不需要这个。

## 如果满足这些条件，说明它在工作

- 它询问接收者以及你需要什么反馈，然后停止提问。关于主题本身的问题是 skill 偏离轨道的标志。
- 你列为"我需要什么反馈"的每个条目都能在文件中追溯到对应的问题。
- 问题读起来是针对接收者知道的什么，而不是你自己的开放式问题逐字复制下来。
- 你可以把文件交给不在对话中的人，他们会知道为什么收到它以及何时之前需要回复。
- 收回的答案可以作为新一轮 grilling 的可用输入，而不是一组新的问题。

## 定位

`to-questionnaire` 是一个随时可调用的独立 skill。它位于你自己知识的边界上，下一步是另一个人而不是另一个 skill——通常是在流程中，当规划因为不属于你决定的事情而停滞时。

它的邻居是 [grill-me](https://aihero.dev/skills-grill-me)，两者的区分在于答案在哪里：grilling 挖掘你自己，问卷挖掘别人。收回的内容是原始材料——可以投入另一轮 grilling，或者如果工作要走向构建，可以投入 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)。当你不确定哪个 skill 适合当前情况时，[ask-matt](https://aihero.dev/skills-ask-matt) 会为你路由。

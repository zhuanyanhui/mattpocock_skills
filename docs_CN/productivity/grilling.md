## 它做什么

`grilling` 是在任何人采取行动之前，对计划、决策或想法进行压力测试的面谈循环。它将主题映射为一棵**决策树**——每个决策都会分支出挂在它上面的其他决策——然后逐个分支地追问你，直到没有任何内容被默默假设。

它不会一次只问一个问题，也不会一次性问完所有问题。每个**轮次**问完整的**前沿**（frontier）：每个前置条件已经落地的决策，仅此而已。如果一个问题依赖于另一个问题，它们绝不会出现在同一轮中——一个取决于尚未开放答案的问题属于后续轮次。你的答案会落地决策，前沿向外推进，下一轮就问那些被解锁的内容。十三个问题通常会在三轮左右完成，而不是十三轮。

## 何时使用

输入 `/grilling`，或者当任务匹配时 [agent](https://www.aihero.dev/ai-coding-dictionary/agent) 会自己调用它。这是追问家族中唯一模型调用的 [技能](https://www.aihero.dev/ai-coding-dictionary/skill)，这也是你很少手动输入它的原因：通常是你输入的某个技能在为你运行它。

直接输入 `/grilling` 只会得到纯面谈，没有额外的东西。当你想要更多时：

| 你有的情况 | 选择 |
| --- | --- |
| 你不在一个工作目录中 | [grill-me](https://aihero.dev/skills-grill-me)——同一个 [会话](https://www.aihero.dev/ai-coding-dictionary/session)，agent 永远不会自己触发的名称 |
| 你在工作目录中 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs)——同一个会话，并且会边进行边写 `CONTEXT.md` 和 ADR |
| 一个太大无法在一个会话中容纳的工作量 | [wayfinder](https://aihero.dev/skills-wayfinder)——绘制决策地图并在决策任务中运行追问 |
| 谈话无法解决的疑问——某个东西应该长什么样或感觉如何 | [prototype](https://aihero.dev/skills-prototype)——构建一次性版本，然后回来 |
| 你自己的某个技能需要面谈 | 从其中调用 `/grilling`，而不是重新写一个面谈 |

## 轮次、前沿和谁来决定

三个概念支撑了整个技能。

**决策树**是主题的模型：带着挂在上面的其他决策的决策。**前沿**是所有前置条件都已经落地的决策集合——是唯一可以诚实地被问出的问题。**轮次**是一个完整被问及并完整被回答的前沿。

在一轮中，每个问题都以固定格式出现：在 `❓` 后编号并加标题，然后是正文，然后是 agent 的推荐答案，独占一行 `➡️`。这正是让一轮可以通过编号回答的原因——"1 是的，2 第二个选项，3 不行，原因是……"——而不是通过引用问题回来。这种格式有一个已知的摩擦点：推荐答案有时会*反驳*问题本身的措辞，所以同意推荐答案意味着对问题回答"不"。遇到这种情况时，回答推荐答案并说明即可。

设计的另一半是事实和决策的分离。事实是技能自己的工作：当前沿问题需要 [环境](https://www.aihero.dev/ai-coding-dictionary/environment) 可以落地的东西时，它会派一个 [子 agent](https://www.aihero.dev/ai-coding-dictionary/subagent) 去查找，而不是问你。它不会因此阻塞——只有运行中的探索下游的问题才会等待。决策是你的，它必须等待。一个运行 `grilling` 的 agent 如果自己回答自己的决策，那是打破了技能，而非宽松地解释。当前沿为空时会话结束，在你确认你们已达成共同理解之前，它不会对你所同意的内容采取行动。

诚实的局限：前沿是 agent 的判断，而非计算出的图。它可能把两个问题放在一轮中，然后才发现其中一个答案本应改变另一个。除了告诉它之外没有防护，这会在下一轮中重新打开受影响的分支。

## 常见问题

**我可以回到一次只问一个问题的模式吗？**
可以，而且很大一部分用户正是这样做的。在你的全局 `CLAUDE.md` 中添加这行：

```
When grilling, ask one question at a time.
```

基于轮次的默认模式确实存在争议。阅读速度较慢、使用第二语言工作、或使用顺序格式作为专注脚手架的用户，都反映一次一个的节奏更适合他们，而且退出选择是被支持的而非仅仅被容忍。

**`/batch-grill-me` 去哪了？**
进了这个技能。基于轮次的提问曾短暂作为独立技能发布，随后移入了 `grilling` 本身，所以所有构建在该原语之上的技能——`grill-me`、`grill-with-docs`、`triage`、`wayfinder`——都一次性获得了它。没有可安装的 `batch-grill-me`，也没有独立的顺序技能；上面那行 `CLAUDE.md` 就是回到一次一个的方式。

**一次问完整轮必然会丢失我早先回答本应引发的问题。不是吗？**
这是对轮设计最常见的反对意见，而前沿正是对此的答案：一轮只包含彼此不依赖的问题，所以一轮中的任何答案都不会使同轮中的另一个问题失效。答案仍然会重塑所有下游内容——下一轮是重新计算的，不是预写的。你丢失的比"一次性问完所有问题"暗示的要少，但也比什么都没有要多——见上面前沿的局限。

**它问完了问题就开始构建代码了。**
确认机制正是为此存在的：当前沿为空时技能并未完成，而是当你说理解已共享时才完成。较弱和较快的 [模型](https://www.aihero.dev/ai-coding-dictionary/model) 仍然会打破它——这在低努力或非前沿模型上最常见，它们会把"面谈直到达成共同理解"压缩成几个问题和一个大纲。如果你的也这样，可靠的修复是在你自己的 `AGENTS.md` 或 `CLAUDE.md` 中加一行，告诉 agent 未经许可不要实现。

**它自己回答了自己的问题而不是问我。**
这是运行中的 bug，不是预期行为，这也正是技能和决策在技能文本中被分开的原因。它在另一个技能在"解决这个任务"框架内运行 `grilling` 时最常见出现，周围的上下文读作继续前进的许可证。这也是为什么没有异步模式的原因：有人要求一个读取 GitHub issue 并发布一条统一决策备忘录的变体，那是另一个不同的技能，因为一个没人回答的追问会话产生的是 agent 的意见，而不是你的。

**我可以限制问题数量吗？**
不行，限制是刻意不在范围内的。有些计划需要三个问题，有些需要五十个；固定的上限要么截断了困难的情况，要么在简单的情况下显得武断。用自然语言引导是预期的控制方式——告诉它收尾，或者停下来接受当前进度。如果一次会话运行得非常长，原因通常是范围太大了；把工作拆分，然后逐个追问。

**我单独安装了 `grill-me` 但什么都没发生。**
`grill-me` 是一个单行技能，它整个主体就是"运行一个 `/grilling` 会话"，所以它需要同时安装这个技能。`grill-with-docs` 也一样，此外还需要 [domain-modeling](https://aihero.dev/skills-domain-modeling)。安装整个套装可以避免这个问题；选择性安装意味着也要安装原语。

**`grill-with-docs` 运行了，但它从未加载 `grilling`。**
这是一个真实且未修复的摩擦点，跨 [harness](https://www.aihero.dev/ai-coding-dictionary/harness) 和模型都有报告：一个命名了另一个技能的技能并不能可靠地导致那个技能被加载，而 `grill-with-docs` 命名了两个。标志是会话一次性问完所有问题，没有附带推荐答案——那是模型在即兴面谈，而非运行这一个。直接向 agent 询问它是否加载了 `grilling` 和 `domain-modeling` 通常可以恢复。

## 它生效的标志

- 一轮以编号列表的形式到来，每个问题的推荐答案在单独的 `➡️` 行，你可以通过编号回答整轮。
- 一轮中没有任何问题需要先回答同轮中的另一个问题。
- 后续轮次问到了首轮不可能问到的内容。
- 它会去查找事实——读取文件、派子 agent——而不是问你它能自己查到的东西。
- 后台运行的研究不会拖慢轮次；只有依赖它的下游问题会等待。
- 它在最后停下来，要求你确认理解已共享，而不是开始工作。
- 问题数量保持高位而轮次数量保持低位。

## 在体系中的位置

`grilling` 是一个**原语**，不是你要调度的步骤：面谈技术的唯一真实来源，集中维护在一个地方，让每个需要面谈的技能都调用它而非自己发明一个。[grill-me](https://aihero.dev/skills-grill-me) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 是它的两个用户调用的前门，而 `grill-with-docs` 是主构建链开始的地方，在 [to-spec](https://aihero.dev/skills-to-spec) 之前。[wayfinder](https://aihero.dev/skills-wayfinder) 运行它来解决决策任务，[triage](https://aihero.dev/skills-triage) 用来把一个模糊的报告追问成可执行的工作，[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 用来在选定一个候选进行深化后遍历决策树。当你不确定哪个入口适合时，[ask-matt](https://aihero.dev/skills-ask-matt) 会为你路由。
